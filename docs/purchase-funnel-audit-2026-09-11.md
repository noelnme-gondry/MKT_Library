## 1. P0 — 돈이 새거나, 받고도 못 주는 경로

### P0-1. 가상계좌·지연승인 결제자는 이용권을 영구히 못 받는다

`src/lib/subscription/paymentVerification.js:4`는 `payment.status === "DONE"`만 이용권으로 인정한다.
가상계좌는 승인 즉시 `WAITING_FOR_DEPOSIT`으로 돌아오므로 `confirmPayment`가 `PAYMENT_NOT_COMPLETED`를 던지고, 화면은 "승인 결과를 확인하지 못했습니다. 다시 결제하지 말고 승인 확인을 재시도해 주세요"를 띄운다.

며칠 뒤 실제 입금이 되면 `reconcilePaymentWebhook`이 DB를 `paid`로 바꾸지만,

- 그 브라우저의 `gop_payment_pending` 쿠키는 `Max-Age=86400`으로 이미 만료됐고,
- `gop_payment_access` 쿠키는 **한 번도 발급된 적이 없다**(승인 성공 응답에서만 발급).

즉 **입금 완료 = DB는 유료, 사용자는 무권한**. 코드에 복구 경로가 없다.

> 확인 필요: Toss 위젯 `variantKey:"DEFAULT"`가 현재 상점 설정에서 가상계좌·계좌이체를 노출하는지. 노출 중이라면 즉시 결제수단을 제한하거나 대기 상태 처리를 만들어야 한다.

### P0-2. 쿠키 하나가 유일한 신원이라, 쿠키 소실 = 이용권 소실

`readPaymentAccess`는 `gop_payment_access` 쿠키(또는 복원 코드)로만 동작한다.
국내 모바일 결제 현실 — 카카오페이·토스앱 복귀가 별도 인앱 브라우저/새 컨텍스트에서 일어나는 경우 — 에서 쿠키가 따라오지 않으면 `confirmPayment`가 `INVALID_ORDER`로 실패하고, 화면은 **"다시 결제하지 마세요"만 반복**한다.

복원 코드는 승인 성공 화면에서만 발급되므로 이 사용자에겐 애초에 존재하지 않는다. 남은 수단은 고객센터뿐인데, 사용자는 주문번호(`gop_<uuid>`)를 알 방법이 없다(Toss 영수증에서만 확인 가능).

### P0-3. 영수증 메일이 구조적으로 발송될 수 없다

`src/lib/account/accountMail.js:45` — 영수증 큐 삽입 조건이

```sql
WHERE p.account_id IS NOT NULL AND p.status='paid' AND p.mode='live'
```

그런데 파일럿 설정(`ACCOUNT_ALLOWED_EMAILS` 지정)에서는 `paymentServer.js:13`의 `requiresPurchaseAccount()`가 false → **모든 신규 구매가 익명 = `account_id` NULL**.

결과: P0-1·P0-2로 이용권을 못 받은 구매자에게 보낼 **증빙도, 연락 수단도, 서버가 아는 신원도 없다.**

### P0-4. 공개 사이트가 test 모드로 열려 있다

`docs/payment-audit-followup-2026-09-11.md` 기록 기준 운영 config는 `enabled=true, mode=test`다.
`syncOrder` / `readPaymentAccess`는 주문의 `mode`가 현재 config와 **일치하는지만** 확인하므로, 테스트 결제로 승인된 주문도 진짜 1개월 Pro를 발급한다. `/subscription`은 헤더 마이페이지 메뉴에서 공개 도달 가능하고, 화면에는 "테스트 결제 · 실제 청구되지 않음"이라고 안내까지 되어 있다.

**매출 0 + 유료 기능 무료 배포.** 라이브 키 전환 전까지 결제 섹션을 비노출하거나 접근을 제한해야 한다.

### P0-5. 로그인 실패가 팝업의 raw JSON으로 끝난다

`src/app/api/account/callback/route.js:2` — 실패 시 `accountError(error)`가 `{"error":"INVALID_LOGIN"}` 400을 **팝업 창에 그대로 렌더**한다. 팝업은 닫히지 않고 `postMessage`도 없어 원래 화면은 상태를 모른다.

하필 #858에서 도입한 `ACCOUNT_ALLOWED_EMAILS` 허용목록 때문에 **목록 밖 방문자 전원이 Google 동의를 마친 직후 이 화면에 도착**한다. 퍼널에서 가장 비싼 지점에서 JSON을 보여주는 셈이다.

이메일 로그인도 같다. `finishEmailLogin`은 `gop_email_browser` 쿠키를 요구하는데, 메일 링크는 Gmail·카카오 인앱 브라우저에서 열리는 것이 기본값이라 쿠키가 없다 → 같은 JSON 화면.

## 2. P1 — 전환을 깎는 설계·모순

### P1-6. 14일 체험이 가격 페이지에 한 글자도 없다

UI 노출을 grep으로 전수 확인한 결과, 체험 문구는 `src/components/AccountArchive.jsx:69` 한 문단과 개인정보처리방침뿐이다. 플랜 비교표·구매 모달(`SubscriptionPurchasePrompt`)·다운로드 게이트 어디에도 "무료 체험"이 없다.

시작 조건도 **"계정 보관함에서 로컬 결정 메모를 골라 동의하고 저장"** — 보고서를 받으러 온 사람이 우연히 밟을 수 없는 경로다. 시작 시점은 서버가 조용히 `trial_started_at`을 기록하는 암묵적 방식이고, 남은 일수 카운트다운이 화면에 없다. 사용자는 2주 뒤 "체험 종료" 한 줄만 본다.

### P1-7. 같은 화면에서 "현재 플랜 Pro" ↔ "결제하세요"가 동시에 뜬다

`src/components/SubscriptionPage.jsx:51`은 `paid={hasPaidAccess(entitlement, now)}`(체험 포함)을 넘겨 Pro 카드에 "✓ 현재 이용 플랜"을 찍는다.
바로 아래 `SubscriptionCheckout`은 `paid = hasPaidAccess(...) && !entitlement?.trial`이라 결제 버튼을 띄운다.

체험 사용자는 "이미 Pro인데 왜 결제창?"을 보게 되고, 비교표에는 만료일 경고도 없다. AGENTS §7의 **"그룹배지 ↔ 상세 판정 모순"** 재발이다.

### P1-8. 구매한 적 없어도 "구매 이용권 연결" 버튼이 뜨고, 누르면 엉뚱한 말을 한다

`AccountArchive.jsx:78` 버튼 → `claim-pass`가 구매 없음에 `PRO_REQUIRED`를 던짐 → `AccountArchive.jsx:53`의 공용 에러 핸들러가 `PRO_REQUIRED`를 **"체험이 종료됐습니다"**로 번역한다.

체험을 시작한 적도 없는 사용자가 체험 종료 통보를 받는다. 버튼 자체도 구매 이력 유무와 무관하게 항상 렌더된다.

### P1-9. 로그인하면 유예가 72시간 → 5분으로 줄고, 복원 코드 버튼이 사라진다

`src/lib/account/archiveContract.js:24`의 계정 entitlement는 `offlineUntil: now + 300000`이고 `payment` 플래그가 없다. `refreshAccount`가 결제 entitlement를 덮어쓰므로(만료일이 같으면 `>` 조건에 걸리지 않는다) 구매자가 로그인하는 순간:

1. 오프라인·장애 유예가 72시간 → **5분**으로 축소
2. `entitlement.payment`가 사라져 체크아웃의 "이용권 복원 코드 보관" 버튼이 렌더되지 않음 → **재방문한 유료 사용자는 복원 코드를 다시 받을 수 없다**

여기에 `WorkspaceStorageBootstrap`의 갱신 주기가 240초 / 유효 300초라 **여유가 60초뿐**이다. 백그라운드 탭 타이머 스로틀링이나 일시적 네트워크 실패 한 번이면 유료·체험 사용자가 다운로드를 눌렀을 때 구매 모달을 본다.

### P1-10. `/subscription` 첫 화면이 구매가 아니라 가입 폼이다

히어로 바로 아래가 `<div id="account-archive"><AccountArchive/></div>`다. "결정 메모를 계정에 보관"이라는 **다른 기능**의 로그인 UI가 플랜 비교·보고서 미리보기·가격보다 먼저 온다. 구매 의도로 들어온 사람이 처음 만나는 것이 Google 버튼이다.

### P1-11. 공개 전환 시 "결제 전 로그인 필수"는 전환 킬러다

`paymentServer.js:13`의 `requiresPurchaseAccount()`는 허용목록을 지우는 순간 true가 되어, 로그인 없이는 결제 버튼 자체가 렌더되지 않는다.

이미 `claim-pass`(사후 연결)가 구현돼 있으므로 **결제 → 승인 화면에서 "이 결제를 계정에 연결" 유도**가 같은 목적을 달성하면서 이탈이 훨씬 적다.

부수 문제: "계정 허용목록"이라는 운영 변수 하나가 **결제 정책까지 뒤집는 숨은 결합**이다. 두 스위치를 분리해야 한다.

### P1-12. `begin_checkout` 계측이 오염됐다

`SubscriptionCheckout.jsx:118`의 auto-prepare가 **페이지 방문만으로** `checkout_requested` + `begin_checkout`을 전송하고 DB에 pending 주문 행까지 만든다.

즉 `begin_checkout ≈ subscription_viewed`가 되어, 정작 알고 싶은 **"가격 보고 이탈" vs "결제창에서 이탈"** 구분이 불가능해진다. 버려진 주문 행도 방문자 수만큼 쌓인다. 의도(결제 버튼 클릭)와 준비(위젯 로드)를 분리해야 한다.

## 4. 잘 된 것 (되돌리지 말 것)

- **이중청구 방어**: Toss HTTP 호출 중 DB 커넥션·행 잠금을 보유하지 않고, 영속 멱등키를 재사용한다(`confirmPayment`).
- **웹훅 페이로드 불신 + 원천 재조회**, `timingSafeEqual` 소유권 확인, `paymentOrigin` 카노니컬 호스트 고정.
- **결제 전 로컬 스냅샷 → 복귀 복원**(24시간 만료, 프로젝트 변경 감지). 이탈 방어 장치로 유효하다.
- **블로그 인라인 CSV 분석**(#856)은 상단 퍼널로 유효하다. 다만 여기서 보고서·구매로 이어지는 다음 행동이 약하다.

## 5. 권장 처리 순서

1. **라이브 전환 전까지 결제 섹션 비노출** (P0-4). 지금은 Pro를 무료로 배포하는 상태다.
2. **콜백 실패를 HTML 화면으로 교체** (P0-5). 허용목록 밖 사용자에게 "현재 제한 검증 중" + 익명 분석 계속하기 링크. 작업량 소.
3. **결제 신원을 쿠키 하나에 걸지 않기** (P0-1·2·3):
   - 결제 시 이메일 1칸 수집 → 주문번호·복원 코드 메일 발송
   - `WAITING_FOR_DEPOSIT` 전용 대기 화면 + 입금 웹훅 시 메일로 이용권 전달
   - 여기까지 되기 전에는 Toss 콘솔에서 가상계좌·계좌이체를 비활성화
4. **체험을 가격 페이지·다운로드 게이트에 노출** (P1-6), 비교표 `paid` 판정에서 체험 분리 (P1-7), claim-pass 메시지 분리 (P1-8).
5. **`begin_checkout` 발화 지점 교정** (P1-12). 안 고치면 앞으로의 모든 퍼널 판단이 틀린 숫자 위에서 이뤄진다.

1·2·5번은 한 PR로 묶을 만하다.
