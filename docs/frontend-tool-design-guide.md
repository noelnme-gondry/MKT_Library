## 0. 이 문서의 역할

이 문서는 단순한 색상·버튼 목록이 아니다. 마케터가 데이터를 넣고, 결과를 이해하고, 신뢰하고, 행동을 정하는 전체 과정에서 **무엇을 먼저 보여주고 무엇을 감출지** 결정하는 기준이다.

적용 범위는 다음과 같다.

- 전체 레이아웃과 정보 밀도
- 타이포그래피·색·간격·표면·경계
- 버튼·토글·탭·필터·스티키 영역
- 카드·KPI·배지·칩·콜아웃·모달
- 차트·표·데이터 미리보기
- CSV/XLSX 업로드와 컬럼 매핑
- 결과·근거·경고·신뢰도 표시
- 로딩·빈 상태·오류·차단 상태
- UI 문구와 KR/EN 동등성
- 모바일·키보드·스크린리더·인쇄
- 디자인 리뷰와 신규 도구 승인 기준

### 문서 간 관계

| 문서 | 역할 |
|---|---|
| `AGENTS.md` | 아키텍처, 데이터 보호, 검증, Git 등 프로젝트 절대 규칙 |
| `design-system-baseline.md` | 공용 컴포넌트와 기술 계약 |
| **이 문서** | 시각 위계, 상호작용, 콘텐츠와 데이터 표현 규칙 |
| 도구별 spec | 해당 도구에만 필요한 예외와 분석 계약 |

기존 공용 컴포넌트와 이 가이드가 충돌하면 임의로 우회하지 않는다. 예외의 이유를 도구 spec에 기록하고, 재사용 가능하면 공용 계약과 이 문서를 함께 갱신한다.

## 1. 디자인 브리프

### 1.1 제품의 구체적인 주제

**Performance Marketing Operator Desk**

광고 운영자가 이번 주 데이터를 보고 원인을 설명하고, 다음 행동 하나를 정하고, 그 판단을 다음 주에 검토하는 작업대다.

### 1.2 핵심 사용자

- 한국 시장의 시니어 퍼포먼스·그로스 마케터
- 여러 채널·캠페인·소재를 동시에 운영하는 실무자
- 통계 전문가는 아니지만 예산과 성과 판단에 책임이 있는 사람
- 민감한 운영 데이터를 외부 서버에 올리기 어려운 사람

### 1.3 모든 도구 페이지의 단일 목적

> 현재 데이터로 답할 수 있는 질문 하나를, 신뢰 수준과 함께 설명하고, 다음 행동 하나로 연결한다.

차트 개수, 기능 개수, 통계 기법 노출은 이 목적보다 중요하지 않다.

### 1.4 시그니처 요소: Decision Tape

Growth Opt Playbook이 기억되어야 할 한 가지 요소는 **Decision Tape**다.

```text
[판단 상태]  결론 한 문장  |  핵심 근거  |  지금 할 행동  |  다음 검토일
```

현재 [`ResultActionCard.jsx`](../v2-migration/src/components/ds/ResultActionCard.jsx)가 이 역할의 기반이다. 모든 도구의 개성은 차트 종류가 아니라, 서로 다른 분석도 같은 Decision Tape로 끝난다는 일관성에서 나온다.

## 2. 첨부 레퍼런스에서 가져올 것

첨부된 대시보드가 깔끔해 보이는 이유는 흰색 배경이나 둥근 카드 자체가 아니다.

### 가져올 원칙

1. **한 화면에 주 작업 영역이 하나다.**
2. 사이드바는 위치를 알려주고, 본문은 판단을 돕고, 우측 레일은 보조 문맥만 제공한다.
3. KPI는 작은 수의 스트립으로 모여 있고 서로 경쟁하지 않는다.
4. 차트는 배경 장식이 아니라 화면의 중심 질문 하나를 설명한다.
5. 행과 객체 사이의 넉넉한 여백이 시각적 그룹을 만든다.
6. 테두리와 그림자가 약하며 활성 상태만 색으로 강조한다.
7. 모든 조작 요소가 항상 보이지 않고 현재 단계에 필요한 것만 보인다.

### 그대로 가져오지 않을 것

- 일반적인 흰색 SaaS 관리자 화면
- 목적 없는 우측 Activity 피드
- 모든 정보를 작은 카드로 쪼개는 카드 갤러리
- 프로필·팀·메시지처럼 현재 제품에 필요 없는 장식적 기능
- 둥근 모서리와 그림자를 많이 쓰면 깔끔해진다는 접근

### 이 제품에 맞춘 해석

| 레퍼런스 요소 | Growth Opt Playbook 해석 |
|---|---|
| 좌측 탐색 | 사용 주기와 의사결정 단계가 보이는 도구 내비게이션 |
| 중앙 Performance 차트 | 현재 질문에 직접 답하는 주 차트 1개 |
| 상단 KPI | 결론을 뒷받침하는 3~5개 핵심 수치 스트립 |
| 우측 Activity | 결과가 나온 뒤에만 보이는 목차·결정·다음 검토 레일 |
| Current Tasks | `이번 주 행동`과 `다음 검토일` |

핵심은 **시각 스타일 복제보다 역할이 분명한 영역 분리**다.

## 3. 핵심 디자인 원칙

### 3.1 결론 먼저, 근거 둘째, 방법론 마지막

기본 노출 순서는 항상 다음과 같다.

1. 지금 무엇을 알아야 하는가
2. 한 줄 결론
3. 핵심 수치
4. 행동
5. 차트와 표
6. 데이터 근거와 한계
7. 계산 방법론

전문 용어와 수식이 결론보다 먼저 나오면 안 된다.

### 3.2 한 화면, 한 주 행동

- 한 시각 영역에는 primary action을 하나만 둔다.
- `분석하기`, `저장`, `다음 주 검증`을 같은 강도로 동시에 노출하지 않는다.
- 현재 단계에서 사용할 수 없는 다음 행동은 숨기거나 이유와 함께 disabled 처리한다.

### 3.3 구조가 장식이다

- 선, 여백, 정렬, 숫자열, 제목 계층으로 정보를 구분한다.
- 내용과 관계없는 번호·아이콘·그라디언트를 장식으로 추가하지 않는다.
- 카드 안에 카드를 반복 중첩하지 않는다.
- 구분을 위해 배경색을 계속 추가하지 않는다.

### 3.4 조용한 기본값, 명확한 신호

- 대부분의 화면은 graphite/paper 중립 표면을 사용한다.
- 파랑은 선택·주 행동, 초록은 검증된 긍정 상태, 주황은 주의, 빨강은 중단·위험에만 사용한다.
- 색이 많아야 하는 곳은 데이터 계열을 구분하는 차트뿐이다.

### 3.5 데이터보다 인터페이스가 더 크게 말하지 않는다

- KPI 값은 크되 카드 자체는 조용하게 유지한다.
- 차트 그리드, 범례, 축, 배경은 데이터보다 낮은 대비를 가진다.
- 강조는 최대 1개 KPI, 1개 차트 계열, 1개 primary action에 집중한다.

### 3.6 기능이 아니라 현재 상태를 보여준다

사용자가 항상 알아야 하는 것은 다음 네 가지다.

- 지금 어떤 데이터를 보고 있는가
- 어떤 범위·기준을 적용했는가
- 분석을 실행했는가, 결과가 오래됐는가
- 이 결과로 행동해도 되는가

### 3.7 데스크톱 우선이되 모바일에서 과업은 끝난다

고밀도 분석은 데스크톱에 최적화할 수 있다. 그러나 모바일에서도 파일 선택, 오류 수정, 분석, 결론 확인, 결정 저장은 완료할 수 있어야 한다.

## 4. 전체 레이아웃

### 4.1 데스크톱 구조

```text
┌───────────────┬──────────────────────────────────────────────────────┐
│ Product nav   │ Global header · breadcrumb · file · utility         │
│ 264px         ├─────────────────────────────────────────────┬────────┤
│               │ Tool title · status · scope controls       │ TOC /  │
│ Weekly        ├─────────────────────────────────────────────┤ review │
│ Monthly       │ Summary / Decision Tape                    │ rail   │
│ Experiments   ├─────────────────────────────────────────────┤        │
│ Learn         │ Primary chart or task                      │        │
│               ├─────────────────────────────────────────────┤        │
│               │ Supporting evidence table / details        │        │
└───────────────┴─────────────────────────────────────────────┴────────┘
```

### 4.2 영역의 책임

| 영역 | 책임 | 넣지 않는 것 |
|---|---|---|
| Sidebar | 위치, 사용 주기, 도구 전환 | 현재 분석의 세부 필터 |
| Global header | 브랜드, breadcrumb, 파일 상태, 언어·테마·검색 | 도구별 모델 파라미터 |
| Tool sticky bar | 도구명, 결과 전체에 영향을 주는 분석 범위 | 차트별 보기 옵션, 긴 설명 |
| Main | 현재 질문, 결과, 근거, 행동 | 전역 내비게이션 중복 |
| Right rail | 목차 또는 결과 후속 문맥 | 항상 켜진 활동 피드 |

### 4.3 콘텐츠 폭

- 전체 앱 최대 폭: `--container-max: 1380px`
- 기본 좌우 gutter: `clamp(18px, 3vw, 42px)`
- 읽기 중심 설명문: 최대 `46em`
- 결과 헤드라인: 최대 `760px`
- 고밀도 표·차트는 본문 폭을 사용할 수 있지만 설명문까지 넓히지 않는다.

### 4.4 표면 깊이

허용 깊이는 세 단계다.

1. 페이지 배경
2. 작업 표면: `.block`, `.card`, `.chart-container`, `.table-wrap`
3. 떠 있는 표면: modal, dropdown, command palette

작업 표면 안에서 별도의 카드 배경을 반복하지 않는다. 내부 구획은 border-top, gap, heading으로 나눈다.

### 4.5 첫 viewport 계약

데이터가 이미 있고 결과가 최신인 도구의 첫 viewport에는 다음 요소가 들어오는 것을 목표로 한다.

```text
도구 제목 + 분석 범위 + 판단 상태 + 결론 + 핵심 수치 + 행동 1개
```

차트 전체가 반드시 첫 화면에 들어올 필요는 없다. 다만 스크롤하기 전에 사용자가 `무슨 결과인지`, `믿어도 되는지`, `무엇을 할지`를 파악해야 한다.

고정 노출 순서는 다음과 같다.

```text
페이지 제목
→ 데이터·분석 범위
→ 현재 결론
→ 핵심 수치
→ 주 차트
→ 상세 표
→ 신뢰·방법론
→ 다음 도구
```

현재 분석을 시작하기 전에 `다음 도구`, `후속 분석`, `플로팅 도우미`가 페이지 제목이나 데이터 준비보다 먼저 나오지 않는다.

## 5. 색상과 테마

현재 `globals.css`의 Operator Desk 토큰을 SSOT로 사용한다.

### 5.1 핵심 팔레트

| 역할 | Dark | Light | 사용 |
|---|---:|---:|---|
| Page background | `#0b1018` | `#eef2f7` | 앱 전체 배경 |
| Base surface | `#111925` | `#f7f9fc` | 앱 셸 |
| Primary work surface | `#141821` | `#ffffff` | 카드·표·차트 |
| Raised surface | `#162131` | `#ffffff` | 활성 패널·overlay |
| Primary signal | `#82aaff` | `#316ee8` | 선택·링크·primary action |
| Secondary signal | `#65d3b3` | `#11866e` | 보조 데이터·성공 |
| Primary text | `#edf3fb` | `#172232` | 제목·핵심 값 |
| Secondary text | `#aebdd0` | `#53647a` | 본문·설명 |
| Muted text | `#71839a` | `#7d8da1` | 메타·비활성 정보 |
| Border | `#2b3a50` | `#d8e0ea` | 작업 표면 경계 |

### 5.2 의미 색상

| 의미 | 토큰 | 사용 조건 |
|---|---|---|
| Success | `--success` | 조건을 충족한 긍정 판정 |
| Danger | `--danger` | 분석 중단, 손실·악화, 파괴적 행동 |
| Warning | `--warning` | 사용자가 확인한 뒤 진행 가능한 위험 |
| Info | `--info` | 중립 안내와 현재 선택 |

색만으로 상태를 전달하지 않는다. 아이콘, 라벨, 문장을 함께 사용한다.

### 5.3 색상 금지 규칙

- JSX에 새로운 hex/rgba를 직접 추가하지 않는다.
- `var(--x)` 문자열을 Chart.js에 직접 넘기지 않는다.
- 초록을 단순 증가, 빨강을 단순 감소에 자동 적용하지 않는다. CPA 증가는 나쁘지만 Revenue 증가는 좋다.
- 6개를 넘는 계열을 모두 강한 색으로 구분하지 않는다. 상위 5~6개와 `기타`로 묶는다.
- 선택 상태와 성공 상태를 같은 색과 모양으로 표현하지 않는다.

라이트 모드의 현재 `--text-muted: #7d8da1`은 흰 표면에서 작은 본문용 대비가 부족할 수 있다. muted 색은 부가 메타에만 사용하고, 안내·경고·버튼·필수 라벨에는 `--text-secondary` 이상을 사용한다.

## 6. 타이포그래피와 숫자

### 6.1 글꼴 역할

| 역할 | 글꼴 | 사용 |
|---|---|---|
| Display | Space Grotesk | 페이지 제목, 결과 헤드라인, KPI 값 |
| Body | DM Sans | 설명, 버튼, 입력, 표 라벨 |
| Data / Utility | JetBrains Mono | 숫자 보조 정보, 축, 짧은 상태, 코드·메타 |

한글은 각 font stack의 시스템 폴백을 사용하되 역할 구분은 유지한다.

### 6.2 권장 크기 계층

| 계층 | 크기 | 규칙 |
|---|---:|---|
| Landing statement | `44–78px` | 랜딩에서만 사용 |
| Long-form page title | `31–52px` | 가이드·주간 리뷰 등 독립 페이지 |
| Tool title | `15–22px` | compact sticky context |
| Result headline | `17–21px` | 결론 한 문장 |
| Section title | `18px` | 한 블록의 질문 또는 내용 |
| Body | `14px / 1.55` | 기본 설명 |
| Compact body | `12px` | 보조 설명과 표 |
| Data/meta | `10–11px` | 단위, 축, 상태, provenance |

9px 이하 텍스트는 장식적 eyebrow 외에는 사용하지 않는다. 행동에 필요한 안내·경고는 최소 12px을 유지한다.

### 6.3 숫자 규칙

- 모든 숫자열은 `font-variant-numeric: tabular-nums`.
- 숫자는 오른쪽 정렬, 텍스트는 왼쪽 정렬.
- 통화·퍼센트·날짜는 공용 `format.js` 사용.
- 큰 수는 KPI에서만 축약할 수 있으며 tooltip 또는 상세 표에 정확값을 제공한다.
- 값이 없는 상태는 `—`, 실제 0은 `0`으로 구분한다.
- 퍼센트 변화와 퍼센트포인트 변화를 구분한다: `+12.4%`, `+3.2%p`.
- 비교에는 기준 기간을 함께 쓴다: `지난 7일 대비 +12.4%`.
- 방향만으로 의미가 결정되지 않는 지표는 `좋음/나쁨`을 자동 색칠하지 않는다.

## 7. 간격·모서리·경계·그림자

### 7.1 간격 체계

기본 리듬은 4px 단위다.

| 토큰 개념 | 값 | 사용 |
|---|---:|---|
| `space-1` | 4px | 아이콘과 라벨 |
| `space-2` | 8px | 같은 객체 내부 |
| `space-3` | 12px | 제어 그룹 |
| `space-4` | 16px | 카드 내부 작은 구획 |
| `space-5` | 20px | 카드 padding |
| `space-6` | 24px | 관련 블록 사이 |
| `space-8` | 32px | 섹션 사이 |
| `space-12` | 48px | 큰 이야기 단락 |

임의의 13px, 19px, 23px을 새로 만들지 않는다. 기존 예외는 마이그레이션 시 가장 가까운 단계로 정리한다.

### 7.2 모서리

| 역할 | radius |
|---|---:|
| 작은 입력·칩 | 6–7px |
| 카드·차트·표 | 10–12px |
| 강조 결과 카드 | 13–16px |
| 원형 배지·토글 thumb | `999px` |

모든 요소를 pill로 만들지 않는다. Pill은 짧은 상태·선택지에만 사용한다.

### 7.3 그림자

- 기본 카드에는 그림자를 사용하지 않는다.
- dropdown, modal, command palette처럼 실제로 떠 있는 객체에만 `--shadow-float`를 사용한다.
- primary button의 약한 glow는 한 영역에 하나만 허용한다.
- hover마다 카드가 크게 떠오르지 않는다. border와 1px 이동만으로 충분하다.

### 7.4 Z-index와 떠 있는 객체

| 층 | 대상 | 원칙 |
|---|---|---|
| 0 | 본문·카드·차트·표 | 기본 문서 흐름 |
| 7–9 | TOC·tool sticky | global header 아래 |
| 10 | global header | 전체 페이지 문맥 |
| 100+ | dropdown·popover | body portal, 현재 trigger 문맥 |
| 1000+ | modal·command palette | focus trap과 backdrop |
| 9999 | 분석 중 block overlay | 정말 전체 입력을 막아야 할 때만 |

새 컴포넌트가 임의로 더 큰 값을 추가하지 않는다. sticky offset과 높이는 `--topbar-h`, `--toolbar-h`, `--sticky-offset` 같은 단일 토큰 계약으로 통합하는 것을 목표로 한다.

## 8. 객체 가이드

### 8.1 객체의 기본 해부

```text
[optional status / eyebrow]
Primary label or value
Supporting explanation
Optional metadata
One action
```

하나의 객체에 두 개 이상의 주 제목, 세 개 이상의 강조 색, 여러 primary action을 넣지 않는다.

### 8.2 Card

사용 조건:

- 한 덩어리로 이해하고 행동할 수 있는 독립 정보
- 다른 카드와 동일 위계로 비교되는 항목
- 결과, 추천, 템플릿 등 명확한 객체

사용하지 않는 조건:

- 단순한 섹션 구분
- 표 안의 모든 셀
- 카드 내부의 설명 한 문단
- 같은 흐름을 여러 작은 박스로 쪼개는 경우

### 8.3 Block

`.block`은 페이지의 주요 섹션이다. 제목은 질문 또는 과업을 표현한다.

좋음:

- `어떤 채널이 이번 주 CPA 상승을 만들었나요?`
- `예산을 어디로 옮길까요?`

피함:

- `분석 결과`
- `Section 2`
- `상세 정보`

### 8.4 KPI strip

- 한 줄에 3~5개를 기본으로 한다.
- 강조 KPI는 한 개만 `is-primary`로 지정한다.
- KPI 라벨은 짧게, 값은 크게, 비교 기간은 작게 둔다.
- 각 KPI를 별도 그림자 카드로 만들지 않고 하나의 스트립 안에서 hairline으로 구분한다.
- 5개를 넘으면 우선순위를 정하거나 다음 행이 아니라 상세 섹션으로 내린다.

### 8.5 ResultActionCard

표준 순서:

1. 상태 신호
2. 평어 결론 한 문장
3. 핵심 수치 3~5개
4. 지금 할 행동 1~3개
5. 데이터 근거·최근 비교
6. 다음 주 검증
7. 방법론·내보내기

한 카드에서 결론을 여러 문단으로 설명하지 않는다. 긴 근거는 접거나 차트·표로 보낸다.

### 8.6 Summary

Summary는 페이지 소개가 아니라 **현재 도구가 답하는 질문과 입력 조건**을 짧게 설명한다.

- 최대 2~3문장
- 첫 문장에 사용자가 얻을 답
- 두 번째 문장에 필요한 데이터 또는 핵심 제한
- 전문 기법명 나열 금지

### 8.7 Callout

| 종류 | 목적 | 행동 |
|---|---|---|
| Info | 방법·단위에 대한 중립 안내 | 없어도 됨 |
| Success | 준비 또는 검증 완료 | 다음 행동 제시 |
| Warning | 확인 후 진행 가능 | 확인할 항목 제시 |
| Danger / Blocked | 결과 사용 금지 | 수정 또는 재시도 방법 필수 |

같은 화면에 경고 callout을 여러 개 쌓지 않는다. `⚠ 3개 확인 필요 — 보기`로 요약하고 세부를 접는다.

### 8.8 Chip, badge, pill

| 객체 | 의미 | 상호작용 |
|---|---|---|
| Chip | 적용 중인 값·필터·파일 | 선택적 제거 가능 |
| Badge | 상태·개수·등급 | 기본적으로 비상호작용 |
| Pill button | 짧은 상호 배타 선택 | 클릭 가능 |

클릭할 수 없는 배지를 버튼처럼 보이게 만들지 않는다. 클릭 가능한 칩은 반드시 `button`으로 구현한다.

### 8.9 Tooltip

- 용어 정의, 축약 이유, 상태의 짧은 보충에만 사용한다.
- 필수 경고, 오류 해결법, 핵심 가정을 tooltip 안에 숨기지 않는다.
- hover뿐 아니라 focus로도 열려야 한다.
- 모바일에는 동일 내용을 여는 버튼 또는 inline 설명이 있어야 한다.

### 8.10 Modal과 dropdown

- Modal은 현재 작업을 중단하고 결정을 요구할 때만 사용한다.
- 가벼운 보조 설명은 `<details>`, popover, inline disclosure를 우선한다.
- 열릴 때 첫 포커스를 이동하고, Tab을 가두고, Escape로 닫고, 닫힌 뒤 호출 요소로 포커스를 복귀한다.
- backdrop 클릭 닫기는 보조 수단이며 명시적 닫기 버튼을 제공한다.
- sticky·backdrop-filter 조상 안의 fixed dropdown은 body portal을 사용한다.

### 8.11 Form field

표준 구조:

```text
Visible label
[input / select] [optional unit]
Help or constraint
Inline error or confirmation
```

- placeholder를 label 대신 사용하지 않는다.
- 필수 여부는 label에서 표시하고 오류가 난 뒤에만 알려주지 않는다.
- 단위는 입력 안의 값과 섞지 않고 suffix 또는 label로 고정한다.
- 숫자 입력은 천 단위 표시가 필요하면 `text + inputmode`와 공용 parser를 사용한다.
- validation은 가능한 한 blur 또는 submit 시 제공하며 사용 중인 모든 키 입력마다 경고하지 않는다.
- 오류는 해당 field 가까이에 놓고 `aria-describedby`, `aria-invalid`를 연결한다.
- 관련 field는 `fieldset/legend`로 묶는다.

## 9. 버튼과 행동 위계

### 9.1 버튼 계층

| 계층 | 스타일 | 사용 예 |
|---|---|---|
| Primary | 채운 primary 색 | `분석하기`, `다음 주에 검증` |
| Secondary | 중립 surface + border | `템플릿 받기`, `다시 시도` |
| Ghost | 투명, 낮은 대비 | `초기화`, `상세 보기`, `인쇄` |
| Danger | danger 색, 확인 필요 | `로컬 기록 모두 삭제` |

한 영역에 primary button은 하나만 둔다.

### 9.2 버튼 문구

- 클릭 후 일어나는 일을 동사로 쓴다.
- `확인`, `제출`, `진행`처럼 결과가 모호한 표현은 피한다.
- 실행 전후에 같은 동사를 유지한다.

| 피함 | 사용 |
|---|---|
| 제출 | 분석하기 |
| 확인 | 매핑 확정 |
| 진행 | 새 파일 분석 |
| 저장 완료 | 결정이 저장되었습니다 |
| 다운로드 | 결과 CSV 받기 |

### 9.3 상태

모든 버튼은 다음 상태를 설계한다.

- default
- hover
- focus-visible
- active/pressed
- disabled + 이유
- loading + 중복 실행 방지
- success feedback
- failure + 복구 행동

disabled 버튼만 두고 이유를 숨기지 않는다. 버튼 근처에 무엇이 부족한지 설명한다.

### 9.4 아이콘

- 아이콘은 라벨을 대체하지 않는 것이 기본이다.
- 반복적으로 학습된 테마·닫기·검색 같은 유틸리티만 icon-only를 허용한다.
- icon-only 버튼은 최소 34×34px, 모바일 44×44px hit area와 `aria-label`을 제공한다.
- 장식 아이콘은 `aria-hidden`.

## 10. 토글·탭·세그먼트·선택 가이드

서로 비슷해 보이는 제어를 의미에 맞게 구분한다.

| 제어 | 사용 조건 | 예 |
|---|---|---|
| Tabs | 서로 다른 콘텐츠 뷰 이동 | 시각화 / 페이싱 / 코호트 |
| Segmented control | 같은 결과의 상호 배타 기준 | CPA / ROAS, KRW / USD |
| Switch | 즉시 적용되는 Boolean | 추세 제거 켜기/끄기 |
| Filter chip | 다중 선택 가능한 범위 | 채널, 국가 |
| Select | 옵션이 많거나 라벨이 긴 단일 선택 | 목표 지표, 모델 모드 |
| Checkbox | 서로 독립적인 복수 설정 | 내보내기 포함 항목 |
| Radio | 설명이 필요한 상호 배타 선택 | 증분 분석 방법 |

### 10.1 공통 규칙

- 현재 선택이 항상 보여야 한다.
- active 상태는 색뿐 아니라 `aria-selected`, `aria-pressed`, check 표시 등으로 표현한다.
- 탭은 arrow key, Home, End 이동을 지원한다.
- 옵션이 5개를 넘고 가로 공간이 부족하면 pill을 계속 늘리지 않는다.
- 잠긴 옵션은 `🔒`만 두지 않고 필요한 데이터나 조건을 설명한다.
- 토글 변경으로 무거운 분석이 다시 계산되면 즉시 실행하지 않고 `결과가 오래됨` 상태와 재분석 버튼을 사용한다.

### 10.2 지표 토글

CPA/ROAS 같은 지표 전환은 다음을 한 세트로 바꾼다.

- KPI 값
- 차트 데이터
- Y축 제목과 단위
- tooltip
- 범례
- 결론 문장
- 표 열과 export

표시 글자만 바꾸거나 차트를 이전 지표 공간에 남겨두지 않는다.

## 11. 스티키·필터 가이드

### 11.1 Sticky stack

허용되는 sticky 계층은 최대 두 개다.

1. Global header
2. Tool context + 분석 범위

탭, 로컬 차트 옵션, 다운로드, 도움말을 추가 sticky layer로 만들지 않는다.

### 11.2 Sticky에 들어갈 수 있는 것

결과 전체에 영향을 주고 스크롤 중에도 현재 범위를 알아야 하는 값만 허용한다.

- 날짜 시작·종료
- 국가·플랫폼·채널·소스
- 전역 성과 기준
- 표시 통화
- 활성 필터 개수와 초기화

다음은 본문 또는 Advanced에 둔다.

- 모델 파라미터
- 차트 하나에만 적용되는 legend·series 선택
- 분석 방법 설명
- 내보내기 세부 옵션
- 다음 분석 추천

현재 [`AnalysisControlBar.jsx`](../v2-migration/src/components/dashboard/AnalysisControlBar.jsx)를 공용 기준으로 사용한다.

### 11.3 필터 위계

```text
분석 범위
  [시작] [종료] [세그먼트 2]                  [초기화]
  └ 세그먼트 펼침: 플랫폼 / 국가 / 채널 / 소스
  [성과 기준: 설치 | 가입] [표시 통화: 원 | 달러]
```

- 기본 행에는 가장 자주 바꾸는 2~4개만 둔다.
- 저빈도 세그먼트는 `세그먼트 N` 아래로 접는다.
- 필터가 적용되면 개수뿐 아니라 가능하면 요약을 보여준다: `KR · Meta 외 2개`.
- 초기화는 필터가 있을 때만 노출한다.
- 필터 적용 후 결과가 0행이면 빈 차트가 아니라 원인과 초기화 행동을 보여준다.

### 11.4 즉시 적용과 적용 버튼

| 조건 | 방식 |
|---|---|
| 단순 로컬 필터·캐시 lookup | 즉시 적용 |
| 100ms 이상 체감되는 집계 | 짧은 loading 상태 후 적용 |
| 통계 모델 재적합 | 변경 내용을 모아 `다시 분석` |
| 결과 의미가 크게 바뀌는 방법 선택 | 확인 후 명시적 분석 실행 |

사용자가 매핑·필터를 편집하는 동안 무거운 계산을 반복하지 않는다.

### 11.5 모바일 필터

- sticky에는 `분석 범위 · N개 적용`과 열기 버튼만 유지한다.
- 상세 필터는 하단 sheet 또는 전체 폭 패널로 연다.
- 적용 중인 필터와 `모두 초기화`가 첫 화면에 보여야 한다.
- sheet의 primary action은 `결과에 적용`, secondary는 `닫기`.
- 화면 아래 고정 UI가 결과의 primary CTA와 겹치지 않게 한다.

## 12. 도구 페이지 상태와 표준 흐름

### 12.1 상태 머신

```text
EMPTY
  → IMPORTING
  → MAPPING_REVIEW
  → READY
  → ANALYZING
  → RESULT
  ↘ BLOCKED / NOT_IDENTIFIED / ENGINE_ERROR

RESULT + 입력 변경 → STALE → ANALYZING → RESULT
```

상태가 바뀌면 화면의 primary action과 안내도 함께 바뀐다.

### 12.2 세 가지 상태 축을 분리한다

`완료`, `신뢰 가능`, `성과 개선`은 서로 다른 뜻이다.

| 축 | 예 | 색·표현 |
|---|---|---|
| 실행 상태 | 준비됨, 분석 중, 완료, 오래됨, 실패 | 진행·시스템 상태 |
| 증거 상태 | 의사결정 가능, 주의, 표본 부족, 식별 불가 | 신뢰 라벨과 근거 |
| 비즈니스 방향 | 개선, 악화, 중립 | 지표 방향에 따른 결과 |

`계산 완료`를 초록색으로 표시해 결과가 좋거나 신뢰할 수 있다는 인상을 주지 않는다. PVM 항등식 실패처럼 계산은 끝났지만 증거가 유효하지 않은 상태는 반드시 별도로 보인다.

### 12.3 Empty

첫 화면에는 다음 네 가지면 충분하다.

1. 이 도구가 답하는 질문
2. 필요한 데이터 한 줄
3. `내 파일 선택`
4. 보조 행동: 템플릿 / 샘플

데이터가 없을 때 빈 차트, KPI 0, 분석 방법론, 다음 도구 추천을 먼저 보여주지 않는다.

### 12.4 Importing / Analyzing

- 현재 작업을 구체적으로 쓴다: `CSV 열을 확인하고 있습니다`, `채널별 반응 모델을 계산하고 있습니다`.
- 무거운 계산 전에 overlay를 먼저 paint한다.
- 진행률을 알 수 없으면 가짜 퍼센트를 만들지 않는다.
- 2초 이상 걸릴 수 있으면 취소 또는 안전한 이탈 가능 여부를 안내한다.
- `prefers-reduced-motion`에서 spinner 외 불필요한 애니메이션을 제거한다.

### 12.5 Mapping review

- 자동 확정된 매핑은 요약하고 접는다.
- 충돌·누락·낮은 확신도만 먼저 보여준다.
- 원본 컬럼, 매핑 대상, 상태, 이유가 한 행에서 연결되어야 한다.
- 필수와 선택 필드를 시각적으로 구분한다.
- 데이터 미리보기는 매핑 중 펼치고 확정 뒤 접는다.
- `분석하기` 앞에 포함 행 수, 제외 행 수, 날짜 범위와 단위를 요약한다.

### 12.6 Ready

- `분석 가능` 상태를 짧게 표시한다.
- primary action은 `분석하기` 하나다.
- 아직 분석하지 않은 상태에서 결과·추천처럼 보이는 숫자를 노출하지 않는다.

### 12.7 Result

표준 순서:

1. ResultActionCard / Decision Tape
2. 주 차트 하나
3. 설명 또는 핵심 원인 표
4. 보조 차트·드릴다운
5. 신뢰·가정·방법론
6. 다음 분석 또는 다음 주 검증

### 12.8 Stale

입력·매핑·필터·분석 설정이 결과 생성 시점과 달라지면 이전 결과를 그대로 최신처럼 보이지 않는다.

- 카드 상단에 `입력이 변경되어 결과가 오래됐습니다` 표시
- 변경된 범위를 짧게 설명
- export와 결정 저장은 비활성화하거나 stale 메타를 강하게 포함
- primary action은 `다시 분석`

### 12.9 Blocked / Not identified / Engine error

세 상태를 구분한다.

| 상태 | 의미 | 화면 행동 |
|---|---|---|
| Blocked | 필수 데이터·형식 부족 | 고칠 컬럼·행과 수정 방법 제공 |
| Not identified | 데이터는 있으나 효과를 구분할 수 없음 | 숫자 대신 이유와 대안 제공 |
| Engine error | 계산 또는 렌더 실패 | 재시도·안전한 복귀 제공 |

오류에서도 CSV가 브라우저에 남아 있는지, 다시 업로드해야 하는지 명확히 말한다.

## 13. 데이터 업로드·매핑 가이드

### 13.1 시작 우선순위

1. CSV/XLSX 로컬 파일
2. 템플릿 또는 샘플 파일
3. 공개 Google Sheets

공개 Google Sheets는 편리하지만 민감 데이터에 부적합할 수 있다. 연결 전에 `공개 링크 전용 · 민감 데이터는 로컬 파일 권장`을 눈에 보이게 표시한다.

### 13.2 Dropzone

- 전체 영역이 `button` 또는 label로 동작한다.
- 제목: `CSV 또는 XLSX 선택`
- 보조: 지원 크기·행 수가 아니라 우선 필요한 파일 형태를 설명한다.
- privacy: `파일은 이 브라우저에서만 처리됩니다`.
- dragover, focus-visible, disabled/importing 상태를 제공한다.

### 13.3 매핑 상태 언어

| 내부 상태 | 사용자 문구 |
|---|---|
| confident | 자동 확인됨 |
| needs_review | 확인 필요 |
| must_confirm | 직접 확인 필요 |
| conflict | 다른 열과 충돌 |
| missing required | 필수 열 없음 |
| ignored | 사용하지 않음 |

확신도 숫자를 그대로 노출하기보다 상태와 이유를 먼저 쓴다. 상세에서는 후보·점수·판정 근거를 제공할 수 있다.

### 13.4 재사용

- 같은 도구·같은 헤더 signature에서만 저장 매핑을 재사용한다.
- 자동 적용 사실을 알리고 `지난 매핑 사용`과 `다시 확인`을 제공한다.
- 다른 도구에서 같은 컬럼명이 다른 의미를 가질 수 있으므로 tool scope를 포함한다.
- 사용자가 로컬 매핑 기록을 확인·삭제할 수 있어야 한다.

## 14. 차트 가이드

### 14.1 차트는 질문으로 시작한다

차트 제목은 시각화 종류가 아니라 사용자의 질문을 말한다.

| 피함 | 사용 |
|---|---|
| CPA 추이 그래프 | CPA가 언제부터 상승했나요? |
| 채널별 막대 차트 | 어떤 채널이 전체 상승을 만들었나요? |
| Scatter Plot | 비용을 늘려도 효율이 유지되는 채널은 어디인가요? |
| Waterfall | CPA 변화가 Volume·Mix·Rate 중 어디서 왔나요? |

### 14.2 질문별 기본 차트

| 질문 | 우선 차트 | 피할 것 |
|---|---|---|
| 시간에 따른 변화 | line / area 최소 사용 | 날짜를 bar로 빽빽하게 표현 |
| 항목 간 크기 비교 | 정렬된 horizontal bar | 3D bar, gauge 남발 |
| 전체 변화의 기여 | waterfall | pie로 양·음 기여 표현 |
| 두 변수 관계 | scatter + 관측 범위 | 점 없는 추세선 단독 |
| 구성비 | stacked bar / 100% bar | 6개 초과 donut |
| 퍼널 | 단계 bar + 절대 인원 | 폭만 있고 수치 없는 장식 funnel |
| 코호트 | heatmap + 모수 | 색만 있고 셀 수치·범례 없음 |
| 분포·불확실성 | dot/interval, boxplot | 평균 하나만 표시 |

### 14.3 기본 구현 계약

- [`chartUtils.js`](../v2-migration/src/utils/chartUtils.js)의 `chartCommonOpts()`와 `CHART_THEME`를 사용한다.
- `responsive: true`, `maintainAspectRatio: false`.
- `prefers-reduced-motion`이면 animation 0.
- 렌더 전 기존 Chart instance를 destroy한다.
- 조건부 마운트 뒤 첫 frame에 `resize()`한다.
- CSS `var()` 리터럴이나 신규 hard-coded hex를 canvas에 전달하지 않는다.
- PNG는 현재 테마 배경을 합성해 내보낸다.

### 14.4 시각 위계

- 주 계열: 2–2.5px line 또는 가장 강한 bar.
- 비교 계열: 1–1.5px 또는 낮은 alpha.
- 기준·예측·추세: dashed line.
- 신뢰구간: 낮은 alpha band + 경계선 최소화.
- 관측값과 모델값은 색뿐 아니라 선 형태·point 형태로 구분한다.
- grid는 Y축 주요선만, X축 grid는 기본적으로 숨긴다.
- point는 데이터가 적거나 hover target이 필요할 때만 보인다.

### 14.5 색상

- 의미 색과 계열 색을 섞지 않는다.
- 한 차트의 강한 계열은 최대 6개.
- 7개 이상은 상위 항목 + 기타 또는 필터를 사용한다.
- 같은 채널은 가능한 범위에서 도구 간 동일한 색을 유지하되 success/danger 색과 충돌하지 않는다.
- 양·음 기여는 부호와 지표 방향을 함께 해석한다.

### 14.6 축과 단위

- Y축 제목에 지표와 단위를 표시한다.
- 통화·퍼센트·인원·건수를 혼합하지 않는다.
- 축 생략이 의미를 과장할 수 있는 bar는 0에서 시작한다.
- line의 0 시작 여부는 변화 판독 목적에 맞추되 축 범위를 명확히 한다.
- dual axis는 두 지표 관계가 핵심일 때만 허용하고 좌·우 색·단위를 직접 연결한다.
- 로그축은 화면과 tooltip에 `로그 스케일`을 명시한다.

### 14.7 Tooltip과 legend

Tooltip 순서:

1. 날짜·항목
2. 정확값과 단위
3. 기준 대비 변화
4. 표본·신뢰구간이 필요하면 한 줄

범례는 plot 위 오른쪽을 기본으로 한다. 공간이 부족하면 별도 series selector로 바꾸며, 범례가 차트 면적의 20% 이상을 차지하지 않게 한다.

### 14.8 높이

| 용도 | 데스크톱 | 모바일 |
|---|---:|---:|
| KPI sparkline | 36–48px | 32–42px |
| 보조 차트 | 220–280px | 240–300px |
| 주 차트 | 320–360px | 280–320px |
| 복잡한 산점도·코호트 | 360–440px | 310–380px |

차트마다 임의 높이를 만들지 않고 역할에 따른 단계 중 하나를 사용한다.

### 14.9 신뢰 표현

차트 가까이에 다음을 표시한다.

- 관측 기간
- 포함된 행·항목 수
- actual / modeled / forecast 구분
- 신뢰구간 또는 표본 부족
- 관측 범위 밖 외삽 영역
- 누락 기간과 보정 여부

모델 예측선이 실제 관측선보다 더 강하게 보이지 않게 한다.

### 14.10 접근성과 데이터 대체

- 차트는 가능한 한 `<figure>`와 `<figcaption>`으로 질문·기간·단위를 묶는다.
- canvas에 `role="img"`와 질문을 설명하는 `aria-label` 또는 주변 문맥을 둔다.
- 차트 핵심 결론은 본문 텍스트에도 존재해야 한다.
- 핵심 수치를 표 또는 다운로드로 확인할 수 있어야 한다.
- 색각에 의존하지 않도록 선 형태, point, 직접 라벨을 병행한다.
- 키보드 사용자가 legend 필터를 조작할 수 있어야 한다.

## 15. 표 가이드

### 15.1 기본 계약

신규 표는 [`DataTable.jsx`](../v2-migration/src/components/ds/DataTable.jsx)를 사용한다. 직접 `<table>`이 필요한 특수 매트릭스는 먼저 공용 컴포넌트 확장 가능성을 검토한다.

필수 요소:

- `<caption>` 또는 구체적인 `aria-label`
- `<thead>`와 `scope="col"`
- 행 헤더가 있으면 `scope="row"`
- 헤더와 셀의 동일한 정렬
- 숫자열 `tnum`과 오른쪽 정렬
- 가로 overflow wrapper
- 빈 상태 문구

현재 `DataTable`은 열 타입을 자동 추정하지 않는다. 숫자열은 `align: "right"`를 명시해야 하며, 정렬 가능한 열만 별도의 sortable contract를 가져야 한다. baseline 문서의 `matrix` 약속은 실제 prop이 생기기 전까지 구현된 기능으로 간주하지 않는다.

### 15.2 열 순서

기본 순서:

```text
식별자 → 핵심 결과 → 비교/증감 → 근거·모수 → 상태 → 행동
```

- 사용자가 가장 많이 비교하는 핵심 값은 왼쪽에 가깝게 둔다.
- 기술적 ID와 상세 진단은 뒤로 보낸다.
- 단위가 다른 값은 열 제목에 단위를 포함한다.
- 같은 의미의 이름·값·상태를 여러 열로 반복하지 않는다.

### 15.3 정렬과 포맷

| 데이터 | 정렬 | 예 |
|---|---|---|
| 이름·라벨 | 왼쪽 | Meta, Campaign A |
| 숫자·통화·퍼센트 | 오른쪽 | ₩12,340,000 / 3.2% |
| 상태 | 왼쪽 또는 중앙 | 판단 가능 |
| 날짜 | 왼쪽 또는 오른쪽, 표 전체 일관 | 2026-08-01 |
| 행동 | 오른쪽 | 상세 보기 |

### 15.4 밀도

- 기본 row height는 36–44px.
- 한 셀의 본문은 최대 2줄. 긴 설명은 row expand 또는 details.
- 행이 30개를 넘으면 상위 원인 우선, 검색·필터·페이지네이션 또는 가상화를 검토한다.
- 합계 행은 상단 또는 하단 한 곳에만 두고 굵은 border로 구분한다.
- zebra striping보다 hover와 hairline을 우선한다.

### 15.5 정렬·필터·드릴다운

- 기본 정렬은 사용자의 의사결정 우선순위에 맞춘다. 최근성 또는 영향도 우선, 동률 시 안정적 2차 기준.
- 정렬 가능한 헤더에만 cursor와 sort icon을 표시한다.
- 현재 정렬 기준과 방향을 `aria-sort`로 제공한다.
- row 전체가 클릭 가능하다면 hover뿐 아니라 focus와 명시적 affordance가 필요하다.
- 행 안에 체크박스와 링크를 과도하게 섞지 않는다.

### 15.6 모바일

우선순위가 낮은 열을 무작정 숨기지 않는다.

1. 핵심 2~3열을 화면에 유지
2. 나머지는 가로 스크롤 또는 행 상세
3. 첫 열은 필요 시 sticky
4. 단위와 상태를 셀 안에 보존
5. `상세 보기`에서 숨긴 내용을 모두 제공

카드로 변환할 때도 행 간 비교 가능성이 사라지지 않는지 확인한다.

### 15.7 표와 다운로드 일치

- 화면과 CSV는 동일 계산 결과를 사용한다.
- 반올림 전 원시값이 다르면 manifest에 표시한다.
- CSV는 BOM + CRLF + RFC4180 escaping.
- 0분모는 빈 값 또는 명시 상태로 내보내며 오류 수식을 만들지 않는다.
- 사용자 라벨이 `=`, `+`, `-`, `@`로 시작하면 spreadsheet formula injection을 방어한다.

## 16. 경고·주의·신뢰 가이드

### 16.1 결과 신뢰 상태

모든 결과는 다음 중 하나를 가져야 한다.

| 상태 | 사용자 라벨 | 의미 |
|---|---|---|
| READY | 의사결정 가능 | 핵심 조건을 충족 |
| CAUTION | 방향만 참고 | 주의 조건이 있으나 제한적 해석 가능 |
| INSUFFICIENT_DATA | 데이터 보완 필요 | 표본·필수 값 부족 |
| NOT_IDENTIFIED | 이 데이터로 구분 불가 | 효과 또는 원인을 식별할 수 없음 |
| ABSTAIN | 판단 보류 | 입증 기준을 충족하지 못함 |
| ENGINE_ERROR | 계산하지 못함 | 계산·렌더 오류 |

내부 enum을 그대로 보여주지 않는다.

### 16.2 경고 작성 형식

```text
[무엇이 문제인지]
[결과에 어떤 영향을 주는지]
[사용자가 무엇을 고치거나 어떻게 해석해야 하는지]
```

예:

> 최근 2주 데이터가 비어 있습니다. 추세가 실제보다 급하게 보일 수 있습니다. 누락된 주차를 추가하거나 분석 기간을 조정하세요.

### 16.3 경고 피로 방지

- 같은 원인의 경고를 차트·표·결과 카드에 반복하지 않는다.
- 화면 위에서는 가장 중요한 경고 하나와 `외 N개`만 보인다.
- 해석을 막는 위험과 참고용 주의를 분리한다.
- 경고가 있지만 진행 가능한지 여부를 명시한다.
- 정상 상태에서 초록 callout을 여러 개 쌓지 않는다.

### 16.4 인과 언어

| 증거 | 허용 표현 | 금지 표현 |
|---|---|---|
| 관측 상관·회귀 | 함께 움직였습니다, 연관 신호 | 원인입니다, 만들었습니다 |
| 비무작위 전후 비교 | 증분으로 추정됩니다 | 광고가 실제로 만들었습니다 |
| 무작위 홀드아웃 | 실험 조건에서 인과 효과로 해석 가능 | 모든 기간·대상에 일반화됩니다 |
| 비유의 | 효과를 확인하지 못했습니다 | 효과가 없습니다 |
| 식별 실패 | 이 데이터로 구분할 수 없습니다 | 효과가 0입니다 |

## 17. UI Text 가이드

### 17.1 목소리

- 사용자의 화면과 업무 언어로 쓴다.
- 능동태와 구체적인 동사를 사용한다.
- 마케팅 문구보다 작업 안내를 우선한다.
- 전문 용어는 필요할 때 평어 설명 뒤에 괄호로 둔다.
- 친절하지만 감정적 사과나 과장된 축하는 피한다.

### 17.2 제목

- 도구명은 명사형으로 유지할 수 있다.
- 섹션·차트 제목은 가능한 한 질문형 또는 결론형으로 쓴다.
- `분석 결과`, `상세`, `Overview`처럼 범용 제목만 사용하지 않는다.

### 17.3 버튼

- `무엇을 어떻게 한다`가 보이는 2~7자 동사구.
- 버튼 라벨과 완료 toast의 동사를 맞춘다.

| 버튼 | 완료 피드백 |
|---|---|
| 매핑 확정 | 매핑을 확정했습니다 |
| 분석하기 | 분석이 완료되었습니다 |
| 결정 저장 | 결정을 이 브라우저에 저장했습니다 |
| 보고서에 추가 | 주간 보고서에 추가했습니다 |
| 결과 CSV 받기 | 결과 CSV를 저장했습니다 |

### 17.4 Empty state

빈 화면은 분위기가 아니라 다음 행동을 안내한다.

```text
제목: 아직 분석할 데이터가 없습니다
설명: 최근 4주 이상의 날짜·비용·전환 열이 있는 CSV 또는 XLSX를 선택하세요.
Primary: 내 파일 선택
Secondary: 예시 파일 보기
Trust: 파일은 이 브라우저에서만 처리됩니다.
```

### 17.5 Error

피함:

- 오류가 발생했습니다.
- 잘못된 입력입니다.
- 다시 시도하세요.

사용:

- `날짜 열 14개 값을 읽지 못했습니다. YYYY-MM-DD 형식으로 바꾸거나 다른 날짜 열을 선택하세요.`
- `실험군과 통제군의 날짜가 3일만 겹칩니다. 공통 기간을 7일 이상 준비하세요.`
- `이 데이터에서는 채널별 효과를 분리할 수 없습니다. 항상 함께 집행된 채널을 합치거나 홀드아웃 결과를 사용하세요.`

### 17.6 신뢰·privacy

좋음:

- `파일은 이 브라우저에서만 처리되며 서버로 전송되지 않습니다.`
- `매핑과 집계 결과만 이 기기에 저장됩니다. 원본 행은 저장하지 않습니다.`

피함:

- `완전히 안전합니다.`
- `100% 익명입니다.`
- 실제 경계를 설명하지 않는 자물쇠 아이콘만 표시

### 17.7 숫자 해석

- 퍼센트와 함께 절대 인원을 병기한다: `+8.2% · 약 164명`.
- 비교 기준을 문장에 포함한다.
- 결과가 반올림됐으면 `약`을 사용한다.
- 권장 행동에는 기준을 쓴다: `CPA가 최근 4주 중앙값보다 20% 높은 소재부터 교체 검토`.

### 17.8 용어 일관성

한 흐름에서 같은 개념은 같은 이름을 사용한다.

| 표준 | 피함 |
|---|---|
| 분석하기 | 실행, 계산, 돌리기 혼용 |
| 매핑 확정 | 컬럼 연결 완료, 스키마 적용 혼용 |
| 분석 범위 | 대상 범위, 필터 기준 혼용 |
| 데이터 교체 | CSV 초기화, 파일 리셋 혼용 |
| 결정 저장 | 액션 기록, 판단 등록 혼용 |
| 다음 검토 | 회고, 리뷰, 결과 입력 혼용 |

### 17.9 KR/EN

- 외부 노출 문구는 같은 작업에서 KR/EN을 함께 작성한다.
- 영어는 한국어 직역보다 동일한 행동 의미를 우선한다.
- 영어 확장 길이를 고려해 버튼 고정폭을 피한다.
- 날짜·숫자·통화는 locale formatter를 사용한다.
- EN 미지원 화면은 일부만 번역해 공개하지 않고 readiness gate를 유지한다.

## 18. 로딩·빈 상태·오류·피드백

### 18.1 Loading

- 300ms 미만 작업은 별도 overlay 없이 버튼 pressed 상태.
- 300ms~2초는 inline spinner와 구체적 상태.
- 2초 이상은 overlay 또는 progress region, 취소·예상 조건 안내.
- 레이아웃이 이미 알려졌으면 skeleton을 사용하되 숫자 모양을 가짜로 만들지 않는다.

### 18.2 Toast

Toast는 완료·저장·다운로드처럼 사용자가 이미 시작한 짧은 행동의 확인에만 사용한다.

- 1개 제목 + 필요하면 1줄 설명
- 핵심 오류를 toast만으로 알리지 않는다.
- `role=status`, `aria-live=polite`.
- 파괴적 실패는 화면 문맥 안에도 남긴다.

### 18.3 오류 복구

- 입력과 매핑이 남아 있는지 표시한다.
- `다시 시도`, `문제 열 수정`, `분석 허브로`처럼 복구 행동을 제공한다.
- 오류 객체나 원자료를 analytics·로그로 보내지 않는다.

## 20. 접근성

### 20.1 필수 기준

- 모든 기능은 키보드만으로 실행 가능.
- 모든 상호작용 요소에 visible focus.
- 상태를 색만으로 전달하지 않음.
- form control에 visible label 또는 accessible name.
- modal focus trap, Escape, focus return.
- 탭은 올바른 `tablist/tab/tabpanel`과 키보드 이동.
- 동적 상태는 적절한 `aria-live` 사용.
- heading 순서와 landmark 유지.
- drag-only interaction 금지.
- chart 핵심 결론의 텍스트 대체.
- `prefers-reduced-motion` 존중.

### 20.2 대비와 텍스트

- 일반 텍스트는 최소 4.5:1, 큰 텍스트와 핵심 비텍스트 객체는 최소 3:1을 목표로 한다.
- muted text에 핵심 행동·경고를 넣지 않는다.
- 10px 미만 텍스트는 읽지 않아도 과업을 완료할 수 있는 보조 메타에만 허용한다.
- 200% 확대에서도 topbar와 sticky 높이가 튀거나 주요 action이 사라지지 않아야 한다.

### 20.3 포커스 순서

DOM 순서는 시각 순서와 일치한다.

```text
도구 제목
→ 데이터 범위
→ 현재 단계의 primary action
→ 결과 결론
→ 차트·표
→ 상세·다운로드·다음 행동
```

### 24.2 신규 코드 금지

- 도구 전용 버튼·pill·table CSS 재발명
- 직접 `<table>` 추가
- 공용 포맷 유틸 대신 `toLocaleString` 반복
- 신규 inline style로 레이아웃·색·타이포를 구성
- Chart.js에 hard-coded theme 색상
- 결과 카드보다 먼저 방법론 패널 노출
- 상태를 색상 또는 emoji 하나로만 전달
- `span onClick`과 drag-only control
- 실행되지 않는 `innerHTML` inline script
- sticky 안 fixed dropdown을 portal 없이 구현
- 모바일에서 핵심 action을 단순히 `display:none`

### 24.3 현재 마이그레이션 부채 기준선

2026-08-01 정적 검색 기준으로 다음 편차가 남아 있다.

- 컴포넌트 JSX inline style 사용 지점이 다수 존재한다.
- 직접 `<table>` 사용은 약 60곳, `<DataTable>` 사용은 1곳이다.
- Chart.js 생성부는 약 49곳이며 일부 도구에 로컬 theme 정의가 남아 있다.
- `globals.css` 상단 Obsidian 토큰과 4,500행대 Operator Desk 토큰이 중복 정의되어 실제 유효 SSOT를 오해하기 쉽다.
- `--bg-3`, `--bg-4`, `--radius`, `--radius-sm`, `--font-body`, `--on-primary`, `--shadow-sm` 등 정의 없이 사용되는 변수 경로가 있다.

이 수치는 즉시 전면 리팩터링하라는 의미가 아니다. 새 코드가 부채를 늘리지 않게 하고, 화면을 수정하는 PR에서 해당 영역만 공용 규약으로 옮기는 기준선이다.

### 24.4 현재 확인된 디자인·동작 편차

| 우선순위 | 편차 | 가이드 기준 |
|---|---|---|
| P0 | `warning`, `ok`, `good` 등 실제 CSS가 지원하지 않는 callout tone 사용 | tone을 `info/success/warning/danger` 계약으로 단일화 |
| P0 | 일부 차트가 로컬 라이트 전용 색 또는 CSS `var()` 문자열 사용 | 모든 canvas 색은 `CHART_THEME/getCssVar`로 해석 |
| P0 | 일부 PNG 버튼이 실제 exporter와 연결되지 않음 | 보이는 action은 반드시 실제 동작 검증 |
| P0 | 모바일에서 sidebar가 숨지만 전체 도구 메뉴 대체가 불분명 | 동일 IA에 접근하는 drawer 또는 메뉴 제공 |
| P0 | 일부 업로드·드래그 매핑이 mouse 전용 | 공용 dropzone과 select/up-down 대안 제공 |
| P0 | 일부 modal이 focus trap·focus return을 제공하지 않음 | `GlobalModals` 패턴을 공용 ModalDialog로 승격 |
| P1 | `.ab-pill`이 선택·상태·일반 action을 모두 표현 | Button/Segmented/Tabs/FilterChip/Badge 분리 |
| P1 | KPI 객체와 empty/error 문구가 도구마다 다름 | KPI strip과 상태 문장 공통화 |

이 표는 구현 완료를 의미하지 않는다. 디자인 리뷰 시 동일한 편차가 새로 늘어나는 것을 막기 위한 알려진 기준선이다.

## 25. 디자인 리뷰 체크리스트

### 25.1 정보 위계

- [ ] 이 화면이 답하는 질문을 5초 안에 이해할 수 있다.
- [ ] 첫 화면에 primary action이 하나다.
- [ ] 결론이 차트와 방법론보다 먼저 보인다.
- [ ] KPI가 3~5개로 제한되고 하나만 강조된다.
- [ ] 카드 중첩 없이 여백과 선으로 그룹이 구분된다.
- [ ] 보조 설명과 고급 방법론이 현재 행동을 방해하지 않는다.

### 25.2 제어

- [ ] 탭·세그먼트·switch·filter의 의미가 맞다.
- [ ] 현재 선택과 적용 범위가 항상 보인다.
- [ ] 무거운 계산을 토글마다 반복하지 않는다.
- [ ] disabled 이유와 복구 방법이 보인다.
- [ ] sticky layer가 두 개를 넘지 않는다.
- [ ] 모바일에서 동일 과업의 대체 제어가 있다.

### 25.3 차트

- [ ] 제목이 사용자의 질문을 말한다.
- [ ] 차트 유형이 질문에 맞는다.
- [ ] 축·단위·기간이 명시돼 있다.
- [ ] actual/model/forecast와 신뢰구간이 구분된다.
- [ ] 색상 외 구분 수단이 있다.
- [ ] `chartCommonOpts`와 `CHART_THEME`를 사용한다.
- [ ] 라이트·다크·조건부 마운트·PNG를 검증한다.
- [ ] 동일 내용을 표 또는 텍스트로 확인할 수 있다.

### 25.4 표

- [ ] DataTable 또는 승인된 matrix variant를 사용한다.
- [ ] label left, number right, header와 cell 정렬이 같다.
- [ ] 빈 값과 0이 구분된다.
- [ ] 기본 정렬이 의사결정 우선순위와 맞다.
- [ ] 모바일 열 우선순위와 상세 접근이 있다.
- [ ] 화면과 export가 동일 계산을 사용한다.

### 25.5 신뢰와 문구

- [ ] `의사결정 가능 / 방향만 참고 / 판단 금지`가 보인다.
- [ ] 데이터 범위·표본·주요 가정·불확실성이 제공된다.
- [ ] 관측과 인과를 구분한다.
- [ ] 오류가 무엇·영향·해결 순서로 설명된다.
- [ ] 버튼이 결과를 구체적인 동사로 말한다.
- [ ] KR/EN 문구와 route가 같은 작업에서 검증됐다.
- [ ] privacy 문구가 실제 저장·전송 경계와 일치한다.

### 25.6 접근성·반응형

- [ ] 360px, 720px, 1100px 이상에서 핵심 과업을 확인했다.
- [ ] 200% 확대에서 겹침·잘림이 없다.
- [ ] 키보드만으로 전체 과업을 완료한다.
- [ ] focus-visible이 모든 상호작용 요소에 보인다.
- [ ] modal focus trap·Escape·focus return이 작동한다.
- [ ] reduced-motion이 적용된다.
- [ ] 핵심 텍스트와 상태가 충분한 대비를 가진다.
