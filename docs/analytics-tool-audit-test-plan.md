# 분석 도구별 UX/UI·로직·분석 과정 감사 테스트 플랜

> 목적: 공개 분석 도구를 한 번에 고치지 않고, **도구 하나를 끝까지 검증·수정·회귀 보호한 뒤** 다음 도구로 넘어간다.
>
> 범위: 운영 대시보드(5-2), 예산 배분(5-3), 실험 분석(5-4), 마케팅 반응(5-18), 핵심 가치 발굴(5-20), 캠페인 성과 변동(5-21), 캠페인 포화도(5-22), 증분 분석(5-23), 콘텐츠 요소 분석(9-1), 소재 분석(9-6). 자동 판단 기록의 IndexedDB 저장은 범위에서 제외한다.

## 1. 완료 기준

도구 하나는 아래 다섯 게이트를 모두 통과해야만 완료다.

| 게이트 | 확인 항목 | 완료 기준 |
|---|---|---|
| UX/UI | 첫 화면·입력·결과·빈 상태·다크/라이트 | 무엇을 입력하고 어떤 행동을 해야 하는지 한 화면에서 알 수 있고, 핵심 결론·수치·다음 행동이 설명보다 먼저 보인다. |
| 데이터 계약 | CSV 매핑·단위·그레인·결측/0/음수 | 필요한 열과 허용 단위가 정직하게 안내되며, 잘못된 입력은 결과 대신 이유와 수정 방법을 보인다. |
| 분석 로직 | 공식·집계·모델 선택·경계값 | 합성 데이터로 예상 부호·합계·판정이 재현되고, 관측 범위 밖/식별 불가에는 단정하지 않는다. |
| 분석 과정 | 입력 → 검증 → 계산 → 결과 → 액션 | 분석 시작 전에는 이전 결과가 섞이지 않고, 분석 중·실패·보류 상태가 구분되며 결과의 근거와 한계가 연결된다. |
| 회귀·배포 | 순수함수·렌더·전체 빌드 | 새 골든 또는 smoke 테스트가 추가되고 `npm run test:all`, `npm run lint`, `npm run build`가 모두 통과한다. |

P0는 잘못된 의사결정, 크래시, 데이터 오집계, 인과 과장, 결과 누출이다. P1은 결과 이해를 방해하거나 잘못 읽게 하는 UX/UI·카피·시각화다. **P0/P1이 0개여야 다음 도구로 이동**한다.

## 2. 모든 도구에 적용할 공통 시나리오

### A. UX/UI 점검

1. 신규 진입: 도구 목적, 필요한 데이터, 첫 행동이 보이는가.
2. CSV 업로드·자동 매핑·수동 매핑: 필수 열, 선택 열, 단위, 매핑 충돌을 이해할 수 있는가.
3. 분석 전: 결과 영역이 숨겨지고 분석하기 CTA가 하나만 있는가.
4. 분석 후: 결론 → 핵심 수치 → 권장 행동 → 근거·상세 순서인가.
5. 빈 데이터·부족 데이터·계산 불가: 빈 차트나 0을 결과처럼 보이지 않고 원인과 다음 행동을 주는가.
6. 긴 표/차트: 범례, 축 단위, 0 기준선, 색의 긍·부정 의미, 모바일 폭에서 읽을 수 있는가.
7. 다크·라이트: 차트 grid/text/범례/선택 상태의 대비가 유지되는가.
8. KO/EN: 공개 페이지의 문구·기능·링크가 같은 의미와 경로로 동작하는가.

### B. 데이터·경계값 점검

| 데이터 케이스 | 기대 동작 |
|---|---|
| 최소 유효 행 | 정확한 결과 또는 표본 부족 보류 |
| 빈 파일·헤더만 있음 | 크래시 없이 업로드/매핑 안내 |
| 결측·문자 숫자·천 단위 콤마 | 파싱 정책을 표시하고 잘못된 행 수를 알려줌 |
| 0 비용·0 성과·음수·Infinity | 분모 0/무한 결과를 만들지 않고 제외 또는 보류 이유 표시 |
| 중복 행·다른 그레인 혼합 | 의도한 grain으로 롤업하거나 위험을 경고 |
| 기간 부족·날짜 불연속 | 모델/비교를 보류하거나 신뢰도 하향 |
| 완전 공선·상수열 | 계산 실패를 숫자 0으로 위장하지 않고 식별 불가로 표시 |

### C. 분석 결과 점검

1. 각 판정마다 `강한 양성 / 강한 음성 / 보류` 합성 fixture를 둔다.
2. 입력이 같으면 결과가 byte-identical인지 확인한다(`Math.random` 금지).
3. 통화·CPA/ROAS·성과 지표 토글은 표·차트·축·다운로드에 모두 같은 정의를 적용한다.
4. 전체 합계와 하위 레벨 합계가 같은지, 분해 항의 합이 총 변화와 같은지 확인한다.
5. 관측 연관은 인과처럼 표현하지 않으며, 불확실성·표본·관측 범위를 결과 가까이에 표시한다.

## 4. 도구 1개를 감사하는 실행 순서

1. **코드·데이터 계약 읽기**: 컴포넌트, 순수 엔진, 기존 tests, CSV mapping을 확인하고 결과 정의를 한 줄로 적는다.
2. **실행 경로 검사**: 빈 상태, 유효 CSV, 분석 전/후, 각 탭·토글·다운로드 경로를 smoke test로 보호한다.
3. **합성 데이터 검사**: 위 표의 최소 5개 시나리오를 순수 함수 테스트로 구현한다. 위험한 판정은 양성·음성·보류를 모두 포함한다.
4. **수학 불변식 검사**: 합계, 단위, 범위, 단조성, 레벨 간 rollup, 토글 동치성을 테스트한다.
5. **UX/UI 교정**: 숫자·행동을 결론 위에 배치하고, 차트 축·0선·범례·색·빈 상태·전문 용어를 정리한다.
6. **회귀 게이트**: 대상 test → 전체 test/lint/build → diff check → PR에서 Railway 배포 확인.
7. **기록**: PR에 발견한 P0/P1, 해결 방법, 추가한 fixture와 남긴 제한을 남긴다. 해결되지 않은 것은 다음 도구로 넘기지 않는다.

## 5. 테스트 구현 규칙

- 순수 계산은 `src/utils/*.test.js`에 fixture로 고정한다. 결과 수치 전체를 과도하게 스냅샷하지 말고, 판정·부호·합계·범위를 검증한다.
- 컴포넌트는 `*.smoke.test.jsx`에서 빈 상태, 유효 데이터, 분석 게이트, 주요 탭/토글의 render throw를 막는다.
- 버그를 고치면 반드시 그 버그를 재현하는 최소 fixture를 추가한다.
- 분석 도구는 “추정 불가/보류”도 정상 결과다. 0·빈 차트·강한 결론으로 대체하지 않는다.
- 차트의 수치는 원값을 유지한다. 표시 포맷만 반올림하고, 축·범례·다운로드의 정의를 하나로 맞춘다.
- 모든 공개 UI 변경은 KO/EN을 함께 확인한다. IndexedDB 자동 판단 기록 저장은 본 감사 범위에서 제외한다.
