## N-1. [P1] 슬림 푸터가 라이트 모드에서 안 읽힌다 — 전 도구 페이지

**측정**(프로덕션 빌드, 1440px, `colorScheme: light`, axe WCAG 2.1 AA)

```
/dashboard  color-contrast 위반 4건
  .site-footer__slim-note   #5c6b80 on #10131a → 3.42:1  (11px)
  a[href$="privacy"]        #53647a on #10131a → 3.07:1  (11px)
  a[href$="terms"]          #53647a on #10131a → 3.07:1
  a[href$="contact"]        #53647a on #10131a → 3.07:1
다크 모드: 위반 0
```

`/tools/*`·`/content/*`·`/dashboard`는 푸터를 **슬림 스트립**으로 대체한다
(`Footer.jsx:15`). 그 스트립의 배경은 영구 다크(`#10131a`)인데 글자색은 테마
토큰(`--text-muted`·`--text-secondary`)에서 온다 — 라이트 모드에서 토큰이 어두워지므로
**어두운 배경에 어두운 글자**가 된다. AGENTS.md §7이 "영구 다크 표면 위 텍스트에 토큰을
쓰면 안 된다"고 이미 적어 둔 함정이 푸터에서 재발했다.

**왜 기존 가드가 못 잡았나**: `themeContrast.test.js`·`buttonContrast.test.js`는 CSS를
정적으로 읽어 토큰 쌍을 검사한다. 이 결함은 **"라이트 토큰 × 다크 표면"이라는 조합**이라
렌더해서 실제 배경을 봐야 드러난다. 정적 검사에 구조적으로 안 보인다.

**하필 걸린 것이 개인정보처리방침 링크다.** 그 문서가 F-03("원본 행을 서버로 보내지
않는다")을 뒷받침하는 유일한 근거이고, 사용자가 CSV를 올리기 직전에 확인하는 자리다.

**개선안**: 슬림 스트립의 글자색을 토큰이 아니라 그 표면 전용 리터럴로 고정한다
(사이드바가 이미 같은 이유로 그렇게 한다). 그리고 가드를 정적 검사에서 **렌더 검사로**
넓힌다 — Playwright + axe를 라이트/다크 각각 도는 검사가 이번 세 건을 전부 잡았다.

## N-2. [P1] 타이포 정리가 1차 표면에서 멈춰 있다

1차에서 결론 카드·스코어카드·매핑 세 표면 85곳만 12px로 올렸다. 지금 다시 세면:

```
CSS  font-size 선언 911곳 중 12px 미만  → 441곳
JSX  인라인 fontSize 중 12px 미만        → 323곳
```

즉 **전체의 약 84%가 남았다**(526곳 중 85곳 처리). 사용자가 "가시성"으로 느끼는 표면이
결론 카드만은 아니다 — 탭 내부 표·차트 범례·필터 바가 전부 남은 쪽에 있다.

**개선안**: 화면 단위로 계속 간다. 다음 순위는 ① 대시보드 탭 내부(표·범례) ② 필터/컨트롤 바
③ 도구별 상세 패널. 가드는 이미 선택자 계열 파생이라 표면을 추가할 때 정규식만 넓히면 된다.

## N-3. [P1] 데모가 "큰 변화 없습니다"로 끝난다

**측정**: `/dashboard` → 예시 1클릭 → 결론 카드 헤드라인

```
"최근 7일: 설치당 비용(CPI) +1.6%. 큰 변화 없습니다."
핵심 수치 4 · 근거 2 · 결론 카드 위치 430px(첫 화면 안) · 4.2초
```

경로는 훌륭하다(1클릭·4.2초·fold 안). 그런데 **첫 경험에서 도구가 아무것도 발견하지
못한다.** 처음 온 사람은 이 도구가 무엇을 잡아내는지 보러 예시를 누르는데, 돌아오는 답이
"큰 변화 없음"이면 도구의 값어치가 화면에 나타나지 않는다.

§12.16이 이미 원칙을 세워 뒀다 — "공유 데모에 실제 신호 부여: 진단 도구 데모가 의미
있으려면 합성 패턴이 신호를 띠어야 한다(노이즈가 크면 곡률이 덮인다)". 5-22를 고칠 때
세운 원칙인데 5-2에는 적용되지 않았다.

**개선안**: `demoData`의 효율 픽스처에 **읽을 수 있는 변화**를 심는다 — 최근 7일에 한
채널의 CPI가 뚜렷이 악화되고 지출은 늘어난 패턴이면, 결론·최대 변동 채널·PVM 요약이
전부 살아난다. `seededNoise` 유지(결정론 §8.3), 엔진 불변, 픽스처만 수정.
**주의**: 이 픽스처는 5-2·5-21·5-22·5-3이 공유하므로 형제 도구 스모크로 회귀를 함께 봐야 한다.

## N-5. [P2] 대시보드 탭이 9개인데 어디부터 볼지 말해주지 않는다

**측정**: 시각화 / 스코어카드 / 시즈널리티 / 페이싱 / 이상탐지 / LTV & ROAS / 코호트 분석 /
퍼널 진단 / 세그먼트 — **9개**. 차트 6개, 페이지 높이 4140px(데스크톱)·6044px(모바일).

claude-ux §2는 상태 버킷을 3개로 접으라고 한다. 탭은 상태 버킷이 아니지만 같은 문제다 —
결론 카드는 "무엇이 문제인가"를 말하는데, 그 다음에 **어느 탭을 열어야 하는지**는 말하지 않는다.

**개선안**(작다): 결론 카드의 다음 행동이 탭을 가리키게 한다. 이미 `dashboardVerdict`가
tone과 최대 변동 채널을 계산하므로 "이상 감지 탭에서 급변한 날을 먼저 보세요" 같은 문장은
있는데, **그것이 실제로 그 탭을 여는 링크가 아니다.** 문구를 탭 전환 액션으로 승격하면
9개 중 하나를 골라 주는 셈이 된다. 탭을 줄이는 것보다 싸고 되돌리기 쉽다.

## N-6. [P2] 모바일이 실제로는 멀쩡하다 — 제품이 스스로를 과소평가한다

1차 C-3에서 "측정 먼저"라고 미뤘던 항목이다. 이제 쟀다.

| 폭 | 예시 버튼 | 결론 카드 | 횡스크롤 | 넘치는 표 | 높이 |
|---|---|---|---|---|---|
| 1440px | 있음 | 렌더됨 | 없음 | 0 | 4140px |
| 390px | 있음 | 렌더됨 | 없음 | 0 | 6044px |
| 320px | 있음 | 렌더됨 | 없음 | 0 | 6284px |

§6.5의 320px 핵심 과업(파일 선택·오류 수정·분석 시작·결론 확인)이 **실제로 완결된다.**
그런데 `MobileToolNudge`는 768px 이하 전 도구에서 "📱 이 도구는 PC 화면에 최적화돼
있어요"라고 말한다. 검색·블로그 유입이 모바일에 몰리는데, 도착하자마자 제품이 스스로
"여기선 제대로 안 됩니다"라고 알리는 셈이다.

**개선안**: 문구를 실측에 맞춘다 — 표·차트가 많은 탭만 넓은 화면을 권하고, 결론 확인과
업로드는 여기서 완결된다고 말한다. **이건 문구만 바꾸는 게 아니라 사실을 정정하는 것이다**
(1차에서 "먼저 고치고 문구를 바꿔야 한다"고 적었는데, 재보니 고칠 것이 이미 고쳐져 있었다).
다만 결론 카드 아래 **탭 내부**까지 320px에서 쓸 만한지는 탭별로 더 봐야 한다.

## N-7. [P2] CSS가 단일 번들

```
.next/static/chunks/*.css  raw 481KB → gzip 77KB   (단일 파일, 전 라우트 공통)
/dashboard  JS 954KB raw · /blog  JS 292KB raw
```

`globals.css` 10,590줄이 하나로 나가서 블로그·용어사전 같은 문서 페이지도 앱 전체
스타일시트를 받는다. gzip 77KB라 재앙은 아니지만, 문서 페이지의 첫 렌더를 막는 자원으로는
크다. (앞서 로컬 서버가 압축을 안 해 1379KB로 보였다 — 압축 후 기준으로 다시 쟀다.)

**개선안**: 급하지 않다. CSS Modules 전환은 토큰 스코핑 문제로 이미 배제됐으므로(§3),
현실적인 선택지는 ① 문서 라우트에서만 쓰는 블록을 별도 파일로 떼어 `blog/layout`에서
import ② 죽은 규칙 제거. ②를 먼저 재는 게 순서다.

## 부록 — 재현 방법

정적 grep으로는 N-1·N-3·N-5가 안 나온다. 프로덕션 빌드를 띄우고 브라우저로 재야 한다.

```bash
cd v2-migration && npm run build && npx next start -p 3100
# 별도 셸에서 Playwright 스크립트로:
#  - axe(@axe-core/playwright)를 라이트/다크 각각 실행 → color-contrast 노드와 실제 색 추출
#  - /dashboard 진입 → .csv-guide-example-btn 클릭 → .result-action-card 대기
#    → 헤드라인·stats·points·좌표·탭 수·canvas 수·scrollHeight 측정
#  - 320/390/1440px에서 documentElement.scrollWidth > clientWidth(횡스크롤) 확인
#  - performance.getEntriesByType("resource")로 transferSize 합산 (로컬 서버는 압축을
#    안 하므로 gzip 후 크기는 빌드 산출물을 직접 gzip해서 잰다)
```
