## 0. 한 줄 결론

현재 제품은 **한 번 분석하기 좋은 도구 모음**에는 상당히 가까우나, **지난주 결론을 이번 주 데이터로 다시 확인하는 운영 시스템**은 약하다.

지금 가장 필요한 것은 새로운 분석 도구가 아니라 다음 세 가지다.

1. 계산 결과를 잘못 확신시킬 수 있는 정확도 위험 차단
2. 첫 분석 이후의 `결정 → 실행 → 다음 주 검토` 연결
3. 실데이터 사용과 재방문을 구분해 볼 수 있는 사용자 리서치·측정 체계

---

## 1. 제품이 해결해야 하는 실제 업무

이 제품의 핵심 사용자는 마케팅 데이터를 구경하려는 사람이 아니라, 정기적으로 아래 질문에 답해야 하는 운영자다.

- 이번 주 성과가 왜 달라졌는가?
- 예산을 어디에서 줄이고 어디에 늘릴 것인가?
- 어떤 캠페인·소재를 유지하거나 교체할 것인가?
- 관측된 변화가 광고의 실제 효과라고 볼 수 있는가?
- 지난주에 내린 판단은 맞았는가?
- 이 결과를 팀과 어떤 근거로 공유할 것인가?

따라서 제품의 단위는 개별 차트나 분석 실행이 아니라 **반복되는 의사결정 한 사이클**이어야 한다.

## 2. 현재 상태 평가

| 영역 | 평가 | 현재 판단 |
|---|---|---|
| 마케터 니즈·기능 범위 | 강함 | Monitor → Explain → Choose → Prove → Learn에 필요한 핵심 도구가 이미 대부분 존재한다. |
| 첫 가치 도달 | 보통 | 데모 접근은 쉽지만 내 데이터 분석으로 넘어가는 경로와 안내가 분산돼 있다. |
| 반복 사용 | 약함 | 분석 이력·결정 기록·주간 검토·주간 보고서가 서로 다른 저장 방식과 화면에 흩어져 있다. |
| 데이터 입력 기반 | 강함 | CSV/XLSX, 자동 프로파일링, 매핑 신뢰도, 충돌 확인, 미리보기와 품질 진단이 마련돼 있다. |
| 분석 신뢰 기반 | 강함 | 표본·기간·방법·경고·재현 정보와 보수적 판정 구조가 다수 존재한다. |
| 현재 계산 정확도 | 주의 필요 | 일부 핵심 도구에서 잘못된 판정을 만들 수 있는 P0 위험이 확인됐다. |
| 도구 간 UX 일관성 | 보통 | 공용 컴포넌트가 있으나 일부 고급 도구는 독자적인 업로드·매핑·표·차트 패턴을 사용한다. |
| 모바일·접근성 | 약함 | 매핑·드래그·사이드바·데이터 교체 흐름이 데스크톱 중심이다. |
| 사용자 행동 측정 | 약함 | 현재 이벤트만으로는 이탈 원인, 데모와 실데이터, 다음 주 재사용을 충분히 구분하기 어렵다. |

### 이미 잘되어 있는 기반

- 랜딩은 도구명이 아니라 실제 마케팅 질문에서 시작한다.
- 가입 없이 사용할 수 있고, CSV가 브라우저 안에서 처리된다는 약속이 명확하다.
- [`CsvUploader.jsx`](../v2-migration/src/components/CsvUploader.jsx)는 파일 입력, 자동 매핑, 충돌, 데이터 품질, 분석 가능 여부를 한 흐름으로 관리한다.
- [`ResultActionCard.jsx`](../v2-migration/src/components/ds/ResultActionCard.jsx)는 결론 → 수치 → 행동 → 다운로드 순서를 공통화한다.
- [`AnalysisBasisBar.jsx`](../v2-migration/src/components/data-import/AnalysisBasisBar.jsx)는 데이터 범위와 품질 근거를 결과 가까이에 둔다.
- [`toolConnections.js`](../v2-migration/src/lib/toolConnections.js)는 분석 결과가 다음 질문으로 이어질 수 있는 연결 구조를 제공한다.

## 3. 핵심 문제: 분석 후 다음 주가 연결되지 않는다

현재의 반복 사용 흐름은 다음과 같다.

```text
질문 선택
  → 샘플 또는 CSV 분석
  → 매핑
  → 결과 확인
  → 접힌 영역에서 결정 기록
  → CSV 또는 보고서 수동 내보내기
  → 이탈
  → 다음 주에 파일·도구·문맥을 다시 찾음
```

결정 기록과 주간 리뷰 기능은 이미 존재하지만 서로 한 흐름으로 느껴지지 않는다.

- [`DecisionReview.jsx`](../v2-migration/src/components/ds/DecisionReview.jsx): 결과 카드 안에서 행동과 검토일을 수동 입력한다.
- [`WeeklyReview.jsx`](../v2-migration/src/components/WeeklyReview.jsx): 앞서 내보낸 결정 CSV를 다시 가져와 실제 결과를 기록한다.
- [`AnalysisHistory.jsx`](../v2-migration/src/components/data-import/AnalysisHistory.jsx): 대시보드에만 최근 결과 요약을 저장한다.
- [`WeeklyReport.jsx`](../v2-migration/src/components/WeeklyReport.jsx): 현재 세션에서 선택한 결과로 보고서를 만든다.

각 기능의 목적은 좋지만 저장 위치와 진입점이 나뉘어 있어 사용자는 하나의 작업을 네 개의 별도 기능으로 배워야 한다.

## 4. 정확도·신뢰도 우선 게이트

아래 항목은 유지율 실험보다 먼저 재현·교정해야 하는 P0 후보다. 수정 전까지 해당 조건에서 결과를 중단하고 `추정 불가`로 처리하는 방향이 안전하다.

### P0-1. A/B 연속형 Welch 검정의 소표본 오차

- 위치: [`abTestMath.js`](../v2-migration/src/utils/abTestMath.js)
- 재현 사례: 자유도 2, `t=4.303`에서 구현값은 `p≈0`, 정확값은 약 `0.05`.
- 위험: 작은 표본에서 개선·악화·무유의 판정이 뒤집힐 수 있다.
- 검증 기준: 검증된 Student-t 누적분포와 외부 참조값을 골든으로 고정한다.

### P0-2. 결과를 본 뒤 증분 기간 자동 선택

- 위치: [`Incrementality.jsx`](../v2-migration/src/components/tools/Incrementality.jsx)
- 현재 위험: 관측 전환율 차이가 큰 구간을 선택한 뒤 동일 데이터로 효과를 계산할 수 있다.
- 영향: 선택편향으로 증분 효과가 과장될 수 있다.
- 제품 원칙: 개입일은 결과를 보기 전에 명시하거나 데이터 계약으로 제공한다.

### P0-3. DiD의 배열 순서 기반 매칭

- 위치: [`incrPrePostMath.js`](../v2-migration/src/utils/incrPrePostMath.js)
- 현재 위험: 실험군과 통제군을 날짜 키가 아닌 배열 순서로 짝지을 수 있다.
- 영향: 누락일·다중 행·정렬 차이가 있을 때 서로 다른 날짜가 비교될 수 있다.
- 검증 기준: 날짜별 선집계 → 정렬 → 날짜 교집합 매칭 → 사전추세 검사.

### P0-4. PVM 0전환 비용 행의 항등식 불일치

- 위치: [`pvmMath.js`](../v2-migration/src/utils/pvmMath.js)
- 현재 위험: 비용은 있으나 전환이 0인 행에서 전체 CPA 변화와 기여도 합이 맞지 않을 수 있다.
- 영향: 불완전한 결과가 `잔차 없는 분해`로 보일 수 있다.
- 검증 기준: 모든 허용 입력에서 `전체 변화 = Volume + Mix + Rate` 항등식을 만족하지 않으면 결과를 중단한다.

### P1 신뢰 백로그

- 증분 매출의 객단가 가정과 신뢰구간
- 예산 배분의 `최적` 표현과 관측 범위 밖 외삽
- 소재 회귀의 자유도·군집·시계열 상관
- `(1,234)`, `10-20`, 잘못된 날짜처럼 모호한 문자열을 조용히 숫자로 바꾸는 파싱
- 도구 구분 없이 저장되는 컬럼 매핑 레시피
- 내보내기 수식의 0분모·라벨 formula injection·화면/CSV 반올림 불일치
- 데이터 내용이 아닌 행 수와 매핑만 반영하는 재현 해시

## 5. 목표 제품 모델: 주간 의사결정 워크스페이스

### 목표 흐름

```text
지난주 결정 확인
  → 이번 주 파일 선택
  → 지난 매핑 자동 적용
  → 지난 기준선과 비교
  → 달라진 핵심 1~3개 확인
  → 이번 주 행동 1개 저장
  → 담당·검토일 설정
  → 다음 주 실제 결과 검토
  → 주간 보고서 반영
```

### 이번 주 화면에 필요한 정보

- 검토 기한이 지난 결정
- 이번 주 검토 예정 결정
- 마지막 사용 도구와 실행일
- 지난 분석의 핵심 결과와 기준선
- 저장된 매핑으로 `새 파일 분석` 시작
- 작성 중인 주간 보고서
- 가장 먼저 확인할 질문 한 가지

### 저장 원칙

원본 CSV는 기본적으로 저장하지 않는다. 아래 메타데이터만 명시적 동의 후 로컬에 저장할 수 있다.

- 마지막 사용 도구와 날짜
- 헤더·매핑 레시피
- 필터와 비교 기준
- 집계된 핵심 결과
- 사용자가 직접 저장한 결정과 검토일
- 보고서 초안

모든 로컬 저장 데이터는 한 화면에서 확인·내보내기·삭제할 수 있어야 한다.

## 6. 개선 가설 우선순위

### P0. 결과에서 바로 다음 주 약속 만들기

현재 빈 결정 양식을 결과 카드가 미리 채운다.

- 분석 결론
- 추천 행동
- 기준 지표와 현재값
- 권장 검토일
- 다음 주 확인할 질문

사용자는 `이 결론을 다음 주에 검증`을 누르고 필요한 부분만 수정한다.

### P0. 재방문 홈 또는 Decision Inbox

다음 방문의 첫 화면에서 `지난주 결정 → 새 데이터 → 변화 → 학습`을 이어간다. raw 데이터 없이도 최근 문맥과 저장된 매핑만으로 복귀 비용을 크게 줄일 수 있다.

### P1. 첫 분석 하나만 추천

[`StartGate.jsx`](../v2-migration/src/components/StartGate.jsx)는 데이터 적합성을 진단하고 가능한 분석을 추천하는 좋은 기반이다. 업로드 직후에는 여러 도구를 같은 강도로 제시하지 않고 다음 순서로 보여준다.

1. 지금 데이터로 가장 먼저 답할 수 있는 질문 하나
2. 그 추천의 이유
3. 보조 분석 1~2개
4. 전체 도구는 `다른 분석 보기` 아래로 이동

### P1. 매핑은 예외만 검토

자동 매핑이 확실한 컬럼은 기본적으로 접고 아래 항목만 펼친다.

- 필수인데 찾지 못한 컬럼
- 두 필드가 같은 컬럼을 주장한 충돌
- 통화·퍼센트·누적/일별 등 단위가 모호한 컬럼
- 사용자가 확인해야 하는 낮은 확신도 매핑

전체 매핑과 원본 미리보기는 언제든 펼칠 수 있어야 한다.

### P1. 공통 신뢰 영수증

모든 결과는 한 가지 상태를 명시한다.

| 상태 | 의미 | 허용 행동 |
|---|---|---|
| 의사결정 가능 | 필수 조건과 핵심 가정 충족 | 추천 행동을 실행 후보로 사용할 수 있음 |
| 방향만 참고 | 품질·표본·가정에 주의 필요 | 추가 검증이나 보수적 액션만 허용 |
| 이 데이터로 판단 금지 | 식별 실패·표본 부족·엔진 오류 | 수치와 다운로드를 차단하고 보완 방법 제시 |

함께 표시할 정보는 데이터 기간, 포함·제외 행, 매핑 확신도, 분석 방법, 주요 가정, 불확실성, 인과 해석 가능 여부, 계산 버전이다.

### P1. 사용 주기별 도구 구조

| 사용 주기 | 도구군 |
|---|---|
| 매주 | 운영 대시보드, 성과 변동, 포화도, 예산 배분, 소재 분석 |
| 월간·분기 | MMM, 증분 분석, Aha 분석 |
| 필요 시 | A/B 테스트, 콘텐츠 요소 분석 |
| 준비·학습 | SOP, 템플릿, 용어 설명 |

도구를 삭제하는 것이 아니라 `언제 쓰는가`를 먼저 알려 선택 피로를 줄인다.

### P1. AAO·GEO 유입의 실데이터 전환

검색·답변 엔진 유입 사용자는 특정 질문을 가진 상태다.

```text
검색 질문
  → 해당 질문이 미리 선택된 /start
  → 필요한 데이터 1줄 안내
  → 내 파일 업로드
  → 해당 분석 실행
```

`내 데이터로 확인`과 `30초 샘플 보기`는 서로 다른 CTA로 분리한다. 명시적으로 실데이터를 선택한 사용자를 자동 데모로 보내지 않는다.

### P2. 모바일 최소 완결 흐름

모든 고밀도 차트를 모바일에서 완전히 편집하기 전에 다음 과업부터 보장한다.

- 파일 선택
- 매핑 오류 수정
- 분석 실행
- 핵심 결론 확인
- 데이터 교체
- 결정 저장

드래그 매핑에는 `컬럼 → 역할 선택` 형태의 터치·키보드 대체 UI를 제공한다. 고밀도 차트·표에는 `데스크톱에서 상세 보기` 안내가 가능하지만 핵심 결론을 모바일에서 숨겨서는 안 된다.

1. 인하우스 앱 퍼포먼스 마케터
2. 여러 광고주를 관리하는 대행사 운영자
3. BI·데이터 분석가 지원이 부족한 그로스/퍼포먼스 마케터

### 권장 표본

- 문제 인터뷰 5명
- 실제 파일 과업 테스트 5명
- 기존 사용자 재방문 테스트 5명
- 6명 내외의 2~3주 다이어리 스터디

한 사용자가 여러 단계에 참여할 수 있으므로 총 모집 인원은 8~12명으로 시작할 수 있다.

### 핵심 과업

> 월요일 오전이다. 최근 4~8주 데이터를 사용해 성과가 달라진 이유를 설명하고, 이번 주에 할 행동 하나를 정한 뒤, 다음 주 새 데이터로 그 판단을 검토해 주세요.

### 관찰 항목

- 원본 파일을 찾고 준비하는 데 걸린 시간
- import 실패와 재시도 횟수
- 자동 매핑 수정 횟수
- 처음 신뢰할 수 있는 결론까지 걸린 시간
- 사용자가 결과의 의미와 한계를 자기 말로 설명할 수 있는지
- 실제 행동을 정할 수 있는지
- 일주일 뒤 도움 없이 이전 작업을 재개하는지
- 사이트 대신 Excel·BI·동료에게 돌아가는 순간

### 인터뷰 질문

- 매주 반복해서 내려야 하는 결정은 무엇인가?
- 이미 받을 수 있는 파일은 무엇이며 준비에 몇 분이 걸리는가?
- 상사나 클라이언트에게 보여줄 숫자는 무엇이며 왜 믿는가?
- 어떤 조건이면 이 추천을 거부하겠는가?
- 분석 결과를 본 다음 실제로 무엇을 했는가?
- 다음 주에는 어디에서 다시 시작할 것으로 예상하는가?
- 공개 Google Sheet 설정이 실제 업무 데이터에서 허용되는가?

### 리서치 판정 게이트

| 관찰 결과 | 먼저 풀 문제 |
|---|---|
| 파일 준비에서 이탈 | 템플릿, import, 매핑, 허용 가능한 연결 방식 |
| 결과는 보지만 행동하지 않음 | 결론 표현, 행동 추천, 결정 기록 |
| 행동하지만 다시 오지 않음 | 복귀 화면, 이전 결과 비교, 검토일·리마인더 |
| 숫자를 믿지 않음 | 계산 정확도, 근거·가정·불확실성 표시 |
| 도구 선택에서 막힘 | 질문 기반 추천과 도구 주기 구분 |

## 8. 제품 지표

### North Star

**주간 실데이터 판단 완료 사용자**

다음 조건을 모두 만족한 사용자로 정의한다.

1. 데모가 아닌 실데이터 import
2. 매핑 확정
3. 유효한 분석 결과 확인
4. 행동 또는 판단 한 개 저장

### 활성화

```text
유입
→ 실데이터 의도 선택
→ import 성공
→ 매핑 확정
→ 유효 결과
→ 행동 저장
```

### 유지

- 28일 안에 서로 다른 두 주에 실데이터 분석 완료
- 같은 도구 재실행률
- 이전 기준선 비교율
- 결정 검토 완료율
- 주간 보고서 생성·내보내기율

단순 페이지 재방문, 데모 실행, 블로그 조회는 제품 리텐션으로 계산하지 않는다.

### 마찰·신뢰

- 첫 실데이터 결과까지 시간
- import 실패율과 실패 단계
- 매핑 수정 횟수
- 품질 blocker 해결률
- 샘플 → 실데이터 전환율
- `이 결론으로 행동 가능` 응답률
- 근거·가정 상세 보기 비율
- 결과 다운로드·팀 공유율

### 측정 보강이 필요한 이벤트

- import 실패와 실패 유형
- 매핑 단계 이탈
- 분석 blocked / not identified / engine error
- 데모 결과와 실데이터 결과 구분
- 이전 결과 비교
- 결정 검토일 도래
- 실제 결과 입력 완료
- 주간 보고서 내보내기
- 결과 신뢰 피드백

현재 [`analytics.js`](../v2-migration/src/lib/analytics.js)의 allowlist와 실제 호출 파라미터도 함께 감사해야 한다. 예를 들어 Dashboard가 보내는 `confidence`는 허용 파라미터와 이름이 달라 기록에서 빠질 수 있다.

## 9. 정기 아이디에이션 운영

| 주기 | 점검 내용 | 산출물 |
|---|---|---|
| 매주 30~45분 | 퍼널 이탈, 오류, 도구별 실데이터 완료, 피드백 5개 | 가장 큰 마찰 가설 1개 |
| 매월 | 실제 사용자 3~5명 업무 관찰, 재방문 코호트, 신뢰 불만 | 가설 3개, 검증할 실험 1개 |
| 분기 | 도구별 사용률·정확도·유지비, 골든 표본 감사 | 강화·통합·숨김 후보 결정 |
| 반기 | 사용자군과 JTBD 변화, 데이터 획득 방식 | 포지셔닝과 도구 구성 재검토 |

### 정기 점검 스코어카드

- [ ] 사용자가 자기 질문에 맞는 시작점을 찾는가?
- [ ] 실데이터 첫 결론까지의 시간이 줄고 있는가?
- [ ] 자동 매핑이 일을 줄이고 예외만 보여주는가?
- [ ] 결과의 상태와 한계를 설명할 수 있는가?
- [ ] 같은 사용자가 다음 주 이전 판단을 이어가는가?
- [ ] 저장 데이터와 개인정보 경계가 명확한가?
- [ ] 모바일에서도 최소 과업을 끝낼 수 있는가?
- [ ] 정확도 골든과 항등식 테스트가 유지되는가?
- [ ] 잘 쓰이지 않는 기능을 계속 전면에 노출하고 있지 않은가?

## 10. 당분간 하지 않을 것

- 사용자 근거 없이 새로운 분석 도구를 추가하지 않는다.
- 리텐션을 만들기 위해 가입을 강제하지 않는다.
- 원본 CSV를 서버나 브라우저 영속 저장소에 자동 보관하지 않는다.
- 공개 Google Sheets가 실제 병목인지 확인하기 전에 복잡한 커넥터를 만들지 않는다.
- 데모 실행과 페이지뷰를 활성 사용자로 계산하지 않는다.
- 신뢰성 위험이 남은 계산에 더 강한 추천 문구를 붙이지 않는다.
- 모든 사용자에게 모든 도구를 같은 우선순위로 보여주지 않는다.
