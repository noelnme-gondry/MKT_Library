## 1. 발견 상세

### F-1-01 [P1][축D·F] WoW가 결측률 변화를 성과 변화로 읽는다

- **입력**: `sparse` 픽스처(90행 · 비용 셀 34% 결측 · 결정론 시드). 통화 KRW 선언, 매핑 완료, 분석 실행.
- **화면**: `핵심 KPI (최근 7일)` → **비용 ₩133.1만 ▲ 17.0% WoW** · 설치 2,773 ▲17.1% · CPA ₩1,352 ▲15.6%
- **독립 재계산**(픽스처에서 직접 합산 — 구현을 거치지 않음)

  | | 직전 주 | 최근 주 |
  |---|---|---|
  | 행 | 21 | 21 |
  | **유효 셀** | **10** | **12** |
  | 결측률 | **52.4%** | **42.9%** |
  | 비용 합 | 1,137,168 | 1,330,848 |
  | 유효 셀당 평균 | 113,717 | 110,904 |

  - **합계 기준 WoW = +17.0%** ← 화면이 보여주는 값 (구현과 일치, 계산은 정확하다)
  - **유효 셀 평균 WoW = −2.5%** ← 결측률 차이를 제거하면
- **기대**: 두 기간의 결측률이 9.5%p 다르면 합계 비교는 성과가 아니라 **관측 수**를 비교한다.
  §8의 "거짓 숫자 금지"와 §7 "결측을 조용히 먹지 말 것"이 걸리는 자리다.
- **실제**: 합계는 정확하고 결측은 0으로 먹지 않는다(빈 셀을 건너뛴다 — 이건 옳다).
  문제는 **건너뛴 개수가 기간마다 다르다는 사실이 비교 옆에 없다**는 것이다.
  사용자는 ▲17.0%를 "비용이 17% 늘었다"로 읽지만, 실제로 늘어난 것은 관측된 셀 수다.
- **원인**: `ScorecardTab.jsx:120~139` — `sum()`이 유효 값만 더하고, 분모(유효 셀 수)는 비교에 들어가지 않는다.
  구조적 문제지 계산 버그가 아니다.
- **한계 고지**: 이 픽스처는 합성이고 결측을 34%로 크게 잡았다. 실사용 CSV의 결측률이 낮거나
  두 기간에 대칭이면 왜곡은 작다. **"실제 사용자 데이터에서 이만큼 벌어진다"는 주장이 아니다** —
  메커니즘이 성립하고, 그것을 막는 장치가 그 화면에 없다는 것까지가 이 발견이다.
- **처방 후보**
  - A안(최소): 두 기간의 결측률이 일정 폭(예: 5%p) 이상 다르면 WoW 카드 옆에 표식 한 줄.
    "직전 주 결측 52% · 최근 주 43% — 합계 비교가 관측 수 차이를 반영합니다."
  - B안: 결측률이 크게 다를 때 **유효 셀 평균 기준 WoW를 병기**. 숫자가 둘이 되는 비용이 있다.
  - C안: 아무것도 안 함 — 근거가 viz 탭에 이미 있으므로(F-1-02가 해결된다는 전제 하에).
  - **A안 권장**: §12.17 "늘어나는 건 답의 정확도지 읽을 거리가 아니다"에 맞춰 한 줄로 끝난다.

### F-1-02 [P1][축F] 결측 고지가 탭 하나 · 접기 안에만 있다

- **실제**: 같은 `sparse` 데이터로 탭만 바꿔 렌더한 결과

  | 탭 | 결론 카드 | 결측 고지 |
  |---|---|---|
  | `viz` | **있음** | 있음 — "이전: … 입력 결측·비정상 셀: **22/42 (52.4%)** / 이후: … **18/42 (42.9%)**" |
  | `scorecard` | **없음** | **없음** |

  나머지 7개 탭(pacing·anomaly·seasonality·ltv·cohort·funnel·segment)도 `scorecard`와 같다 —
  결론 블록이 `Dashboard.jsx:321`에서 `activeTab === "viz"`로 게이트되기 때문이다.
- **가시성 경로**(jsdom DOM 조상 추적 — `textContent`만 보면 "있다"고 잘못 읽는다, §7)
  ```
  SPAN < LI < UL < DETAILS[CLOSED] < DIV < SECTION < SECTION < DIV …
  ```
  viz 탭에서도 **기본 접힌 `<details>` 안**이다. 즉 어느 탭에서도 이 숫자는 클릭 없이는 안 보인다.
- **기대**: 결론을 어느 탭에 둘지는 제품 결정이고, 코드에 근거 주석도 있다
  (`"전체 결론은 첫 진입인 시각화 탭에서만"` — 의도적이다). **결론 카드 위치 자체는 결함이 아니다.**
  문제는 **데이터 품질 고지가 그 결론 카드에 묶여 같이 사라진다**는 점이다.
  품질 경고는 결론의 일부가 아니라 화면 전체의 전제다.
- **원인**: 고지가 `ResultActionCard` → `AnalysisBasisBar`(`buildDataQualityReport`) 안에 있고,
  `ResultActionCard`가 viz 전용 블록 안에 있다.
- **참고**: `buildDataQualityReport.js:97`은 결측률 20% 초과 필드를 `high_missing_rate` 이슈로 이미 만든다.
  **계산은 있고, 그것을 스코어카드에서 읽는 곳이 없다** — §16에 네 번 기록된
  "신호를 만들어 놓고 읽는 곳을 안 배선한 자리"의 다섯 번째 사례다.
- **처방 후보**: 품질 이슈가 `caution` 이상일 때만 필터 바(전 탭 공통, `BasisCurrencyToggleBar` 옆)에
  한 줄 띄우고 눌러서 상세로 보내기. 결론 카드는 지금 자리에 그대로 둔다.

### F-1-03 [P2][축C] 성과 기준 토글이 스코어카드에서 아무것도 바꾸지 않는다

- **입력**: `installs`와 `actions`를 10배 차이로 둔 20일치 데이터로, 토글만 바꿔 같은 탭을 두 번 렌더
- **실제**

  | 탭 | 토글 전환 시 화면 | 비고 |
  |---|---|---|
  | `ltv` | **변함** | `유저(설치)` → `유저(액션)` |
  | `scorecard` | **완전 동일** (270자 ↔ 270자) | — |
  | `funnel` | 완전 동일 (876 ↔ 876) | `denomBasis` 참조 0건 |
  | `segment` | 완전 동일 (410 ↔ 410) | `denomBasis` 참조 0건 |

- **원인**: `ScorecardTab.jsx`는 `denomBasis`를 **읽는다**(:88, :118) — 그리고
  `denom: basis === "actions" ? act : inst`(:128)를 만든 뒤 **그 필드를 아무 데서도 쓰지 않는다**.
  파일 전체에서 `denom` 출현은 4회이고 전부 정의·의존성 배열이다. 소비처 0.
  같은 블록의 `cvr: clk > 0 ? inst / clk : null`(:131)은 기준과 무관하게 **항상 설치 기준**이다.
- **왜 나쁜가**: 그 토글은 스코어카드 **바로 위 필터 바**에 있다. 사용자는 누르고, 아무 일도 안 일어나고,
  같은 토글이 LTV·시각화·코호트에서는 화면을 바꾼다. "눌러도 안 바뀐다"와 "안 바뀌는 게 맞다"를
  구분할 방법이 화면에 없다.
- **처방 후보**
  - A안: `cvr`을 기준 반영(`basis === "actions" ? act/clk : inst/clk`)하고 카드 라벨을 함께 스왑.
    §7 "같은 열에 다른 단위를 담으면서 이름을 안 바꾸면 그게 거짓 숫자다"에 걸리므로 라벨 필수.
  - B안: 스코어카드는 CPI·CPA를 **둘 다** 보여주는 화면이므로 기준 무관이 맞다고 보고,
    `denom` 죽은 필드를 지우고 의존성 배열에서 `denomBasis`를 뺀다(= 무효임을 코드가 말하게).
  - **A·B는 제품 결정이다**(§2.7). 지금 상태(읽지만 안 쓴다)만은 어느 쪽도 아니라 남길 수 없다.

### F-1-04 [P3][문서] 하네스 §12.18이 현재 코드와 어긋난다

- §12.18: *"CPI/CPA·**CVR**·ARPU·리텐션·LTV·**퍼널**을 1토글로 함께 전환"*
- 실측: `FunnelTab`·`SegmentTab`의 `denomBasis` 참조 **0건**. 퍼널은 대신 자체
  `전환 단계(설치→액션)` 선택기를 갖는다 — **더 나은 설계일 수 있으나 문서가 옛 구조를 말한다.**
- §7: *"틀린 규칙은 없는 규칙보다 해롭다."* R-final에서 §12.18을 실측에 맞게 고칠 것.

## 3. 이번 회차에서 내 방법이 틀릴 뻔한 자리

**탭을 단독 렌더한 첫 탐침은 사용자가 도달할 수 없는 상태를 보고 있었다.**
`ScorecardTab`만 렌더하면 KPI가 그려지지만, 실제 화면(`Dashboard`)은 통화 미선언으로
분석을 차단한다. 전체 화면을 렌더하고서야 드러났다 — §7 *"스모크 `beforeEach`의 상태 주입이
진입 경로를 우회한다"*를 그대로 재현한 셈이다. **탐침에도 같은 규율이 필요하다.**

그리고 첫 실행에서 탐침이 **아무것도 출력하지 않았다.** 결함이 없어서가 아니라 출력 자체를
안 하고 있었기 때문이었고, 렌더 길이를 찍어 보고서야 알았다. 탐침은 만들자마자
**한 번 부러뜨려 볼 것**(R0에서 적은 규율이 R1에서 바로 필요했다).
