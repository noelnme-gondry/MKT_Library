# 도구 결함·미흡 전수 감사 플래닝 (2026-09-15)

> **목적**: 발행 도구 전체에서 "모자라고 아쉬운 것"을 **재현 가능한 형태로** 전수 수집한다.
> **주체**: Claude(감사 역할, §6.2). 본 문서는 플래닝이고, 발견은 회차별 파일에 쌓는다.
> **원칙**: 이 회차들은 **코드를 고치지 않는다**. 감사 → 사용자가 우선순위 확정 → 그 다음 구현 PR.

---

## 0. 왜 나눠서 보는가

한 번에 20개 도구를 훑으면 반드시 세 가지가 일어난다(§7 기록된 재발 패턴).

1. **다수가 맞으면 소수의 예외가 안 보인다** — 훑어보면 "다 되어 있다"로 읽힌다(9-6 탭 계약 사고).
2. **프록시를 재고 결론을 말한다** — 앵커 모양을 세고 클러스터 연결성을 말한 사고.
3. **가드가 있다는 사실이 가드가 없다는 사실을 가린다** — 손으로 쓴 배열을 도는 커버리지 테스트.

그래서 이 플래닝은 ① **축을 먼저 고정**하고 ② **회차마다 같은 축을 전수로** 돌린다.
회차 사이에 사용자가 읽고 끊을 수 있게, 회차당 산출물은 **한 파일 · 표 중심 · 발견 순위표**로 통일한다.

## 2. 고정 감사 축 10개 (모든 도구에 동일 적용)

각 축은 **"무엇을 실측하는가"와 "무엇이 결함인가"**를 같이 적는다. 판정이 애매하면 결함이 아니라 `?`(추가 확인)로 남긴다.

| 축 | 이름 | 실측 방법 | 결함 판정 |
|---|---|---|---|
| **A** | 입력·자동매핑 | 실제 플랫폼 export 컬럼명으로 `buildMappingContract` 호출 | 필수 필드가 `__ignore__`로 떨어짐 / 데모 픽스처 헤더로만 검증된 상태 |
| **B** | 그룹·상태 배선 | `TOOL_GROUP` 등록, 미러 스왑, 재진입 후 CSV 잔존 | 읽기·쓰기 그룹 불일치 / `csvGroups` 슬라이스 누락 |
| **C** | 게이트·빈 상태 | 분석 시그 구성 요소, 미매핑·0행·단일값 입력 | 표시 전용 토글이 시그에 포함 / 빈 상태가 날조 또는 무반응 |
| **D** | 엔진 정직성 | 퇴화 입력(상수 종속변수·공선·n≤k·0분산) 직접 호출 | `Infinity`·음수 R²·"계산 불가"를 좋은 등급으로 접음 / 인과 단정 |
| **E** | 불확실성 표시 | CI 유무, 정규화 플래그 소비, non-sig 문구 | 95% CI 없음 / `regularized` 같은 신호를 만들고 안 읽음 / 무유의를 "효과 없음"으로 |
| **F** | 결과 UX | `ResultActionCard` 유무, 결론-근거 2층, 평어 | 결론 없이 표부터 / 전문용어가 접기 밖 / `points` 모양 불일치로 빈 줄 |
| **G** | 산출물 | `DownloadHub` · `csvBody` · 상세문서 | 자체 CSV 조립 / 원천 데이터 되돌려주기 / 다운로드 부재 |
| **H** | 연결성 | `NEXT_TOOL_IDS` · findings publish · `/start` 추천 · 역링크 | 추천에서 영구 부재(사고인지 결정인지 불명) / 들어오는 링크 0 |
| **I** | KR/EN 대칭 | `EN_READY_TOOL_IDS` 포함 여부 + EN 화면 문구 | KO가 EN보다 얇음 / 반쪽 번역 |
| **J** | 가드 실효성 | 해당 도구의 스모크·골든을 **읽고** 무엇을 단언하는지 확인 | 손으로 쓴 배열 / 테스트 내 `?.()` / 조건부 `if` 안의 단언 / 현재 값 그대로 고정 |

**추가 축(회차에 따라 선택)**: `K` 접근성·대비 · `L` 모바일/터치 · `M` 성능(10만 행) · `N` 차트 계약.
이 넷은 도구별로 보면 중복이 크므로 **횡단 회차(R10~R12)에서 전 도구를 한 번에** 본다.

## 5. R0 · 준비 회차 (먼저 1회)

감사가 손 목록을 돌지 않도록, **파생 인벤토리 스크립트**를 먼저 만든다.

- `scripts/audit/tool-inventory.mjs` (임시 스크립트, 커밋은 선택)
  - routeMap → 발행 도구 → 각 도구의 `TOOL_GROUP` · 필수/옵션 필드 · `TOOL_GUIDE` 유무 ·
    `EN_READY` · 스모크 파일 유무 · `NEXT_TOOL_IDS` · `toolSearchContent` 유무 · 데모 픽스처 유무를 **한 표로**
- 출력만으로 **배선 구멍(칸이 빈 곳)**이 먼저 드러난다 → 그 자체가 R0의 발견 목록
- 동시에 각 회차가 쓸 **퇴화 입력 픽스처** 6종을 만든다: 0행 / 1행 / 상수열 / 완전공선 / 전부 0 / 결측 30%

## 6. 진행 규약

- **회차당 1 커밋**(`docs(audit): R<N> …`), 브랜치 `claude/tool-feature-checklist-wqg1qu`.
- 회차 끝마다 사용자에게 **한 화면 요약**(P0/P1 개수 + 가장 아픈 3건)만 보고하고 멈춘다.
- 사용자가 "다음" 하면 다음 회차. 순서 변경·건너뛰기 가능.
- 전 회차 종료 후 **R-final**: 전체 발견을 심각도·비용(줄 수)·의존성으로 정렬한 **구현 로드맵**을 만든다.
  그때 처음으로 "무엇부터 고칠까"를 옵션으로 묻는다(§2.7).
- 감사 중 §7에 남길 일반 교훈이 나오면 그 회차 커밋에 **하네스 갱신을 같이** 넣는다(§15, 압축 1회 동반).

## 7. 이 플래닝이 의도적으로 하지 않는 것

- **코드 수정** — 감사와 구현을 섞으면 "고쳤다"는 주장과 검증이 같은 커밋에 들어간다.
- **점수화·등급** — 도구마다 성숙도가 다른데 점수는 비교를 만들어 놓고 근거를 지운다. 발견 목록이 결론이다.
- **육안 스크린샷 루프** — 판정은 접근성 트리·콘솔·실측 스크립트로(§6.1). 브라우저 확인은 Gondry님 몫.
- **없는 결함 만들기** — 회차별 발견 개수 목표를 두지 않는다. 0건이면 0건으로 적는다.
