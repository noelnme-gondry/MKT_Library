### P1 — 저장 스코프 (A안)

**스키마**

```
meta["weekly-review:projects"] = {
  activeId: "p_xxx",
  projects: [{ id, name, metric, basis, currency, target, period, createdAt, updatedAt }]
}
meta["weekly-review:snapshots"] = { snapshots: [{ ...기존, projectId }] }
store.decisionRecords = [{ ...기존, projectId }]
```

**마이그레이션(가장 위험한 지점).** 읽기 키가 바뀌므로 마이그레이션이 없으면 **기존 사용자에게는 데이터가 사라진 것으로 보인다.** 구 `weekly-review:project` 단일 레코드를 읽어 `id: "default"` 프로젝트로 승격하고, 기존 스냅샷·결정 전부에 `projectId: "default"`를 채운 뒤 구 키를 지운다. 구 키가 없으면(신규 사용자) 빈 목록으로 시작한다. **이 경로는 골든으로 고정한다** — 구 레코드 → 새 구조가 byte 단위로 재현되어야 한다.

**만료.** `RETENTION_MS`(90일) 정리가 프로젝트 단위로도 돌아야 한다. 프로젝트 레코드만 만료되고 그 스냅샷·결정이 남으면 **고아 데이터가 어느 화면에도 안 보이는 채로 저장소를 차지한다.** 정리는 프로젝트 목록에서 파생할 것(§7 "목록을 두 곳에 나열하지 말고 파생시켜라").

**주의**

- 활성 프로젝트는 store 한 곳이 소유하고 나머지는 전부 파생. 프로젝트 목록을 두 번째 배열로 복제하지 말 것.
- 결정 이력·스냅샷 조회는 **전부** `projectId` 필터를 타야 한다. 한 곳이라도 빠지면 다른 고객 데이터가 섞여 보인다 — 읽기 경로 전수를 grep으로 셀 것.
- `/weekly-review`는 `TOOL_GROUP`에서 `efficiency`(`src/lib/toolGroups.js:11`). CSV 그룹 계약은 건드리지 않는다.
- 수학 엔진 불변. 저장·필터층만.

### P3 — 무료 한도 게이트 + 수요 측정

**한도**: 무료 = 프로젝트 **1개**. 두 번째를 만들려는 순간에만 `/upgrade`가 열린다.

**회수 금지 (정직성).** 이미 만든 프로젝트를 잠그거나 지우지 않는다. 제한은 **"새로 만들기" 진입에서만** 걸고, 기존 데이터 접근·내보내기는 무료에서도 영구히 열어 둔다. 저장층이 아니라 생성 진입점에서 거는 이유가 이것이다.

**측정 — 게이트 조회가 곧 전환 신호**

```
upgrade_gate_viewed   { source: "project_limit" | "nav" | "direct", locale }
upgrade_interest_clicked { source, locale }
```

**`source` 없이 페이지뷰만 재면 안 된다.** 푸터·⌘K 등 다른 경로로도 이 페이지에 닿으면 "n개 이상 만들려 했다"는 해석이 깨진다. GA4 주요 이벤트는 **`source = "project_limit"` 조건부로** 만들 것 — 이 조건이 곧 "무료 한도를 실제로 넘으려 했다"의 정의다. 조건식은 P0에서 만든 파생 이벤트 문서에 같이 적는다.

**화면 문구 — 금액을 쓰지 않는다(확정).** 게이트에는 가격을 노출하지 않고 "관심 등록 / 키 요청"만 둔다. 가짜 결제 버튼도 금지(§8, #812에서 이미 못박은 계약) — 결제 폼·카드 입력 없음.

금액이 없으면 **신호는 많아지지만 "29,000원을 낼 의향"과는 다른 것을 재게 된다.** 이 한계를 지표 해석에 그대로 남기고, 가격 수용도는 P5 파일럿에서 **사람에게 직접 묻는 것으로** 따로 측정한다(게이트 클릭 수를 지불 의향으로 환산하지 말 것). 금액 대화는 수동 키 발급 과정에서 일어나므로 구조상으로도 이 쪽이 자연스럽다.

또 하나: 가격이 없다고 "곧 유료가 된다"는 인상을 흘리지 않는다. **무료로 남는 범위(분석 도구 전체·프로젝트 1개·기존 단일 보고서)를 게이트 화면에 명시**해야 오해가 없다.

### P4 — 수동 키 해제 + 유료 기능

#### 4-1. 키 (1개월 기간제 · Supabase 검증)

**스키마는 이미 있다.** `supabase/schema.sql`이 정확히 이 용도로 만들어져 있다(구 접근키 페이월용, 전체 무료 전환 때 미사용으로 남음). 새로 설계하지 말고 그대로 쓴다.

| 구성 | 내용 |
|---|---|
| `access_keys` 테이블 | `key_hash`(평문 미저장) · `expires_at` · `revoked` · `last_used` · `key_label` |
| RLS | 테이블 직접 접근 **전면 차단**(의도적 빈 정책). 노출되는 것은 RPC 하나뿐 |
| `validate_access_key(hash, device)` | `anon`에게만 EXECUTE 허용. `valid` · `expires_at` 반환 |

**월 갱신은 재발급이 아니라 날짜 UPDATE 한 줄이다.** 사용자는 같은 키를 계속 쓴다.

```sql
UPDATE access_keys SET expires_at = NOW() + INTERVAL '30 days' WHERE key_label = '...';
```

이것이 오프라인 서명 키 대신 서버를 쓰는 첫 번째 이유다. 두 번째는 **회수(`revoked = TRUE`)** 로, 환불이나 부정 공유에 대응할 수 있는 유일한 수단이다 — 한 번 발급한 오프라인 서명은 원리적으로 취소할 수 없다. 세 번째는 만료 판정이 서버 `NOW()` 기준이라 **기기 시계를 되돌려도 통하지 않는다**는 것이다.

**클라이언트 서명 검증(Ed25519)은 만들지 않는다.** 서버가 진실의 원천이면 과설계다.

**grace 캐시는 선택이 아니라 필수다.** 검증에 네트워크가 필요해지는 순간, Supabase 장애·사내 방화벽·무료 티어의 비활성 일시정지가 전부 **"돈 냈는데 안 열림"** 이라는 같은 증상을 만든다. 검증 성공 시 `{plan, validUntil}`을 로컬에 캐시하고, **이후 검증이 실패해도 캐시 유효기간 안에서는 통과**시킨다. 잠기는 것은 캐시까지 만료된 뒤뿐이다. (무료 티어의 일시정지 정책은 착수 시점에 실제로 확인할 것 — 기억으로 단정하지 않는다.)

**기기 바인딩은 끈다(확정).** 스키마에 `device_token` 바인딩이 있지만 쓰지 않는다. 마케터는 보통 회사 PC와 노트북을 함께 쓰는데 지금 RPC는 **두 번째 기기를 거부**하고(`device_mismatch`), 파일럿의 목적은 "돈 낼 사람이 있는가"이지 "무단 공유를 막을 수 있는가"가 아니다. 마찰이 신호를 오염시킨다.

구현은 RPC에 `input_device`를 **넘기지 않는 것**이다 — 스키마의 바인딩 분기 두 개가 모두 `input_device IS NOT NULL` 조건이라 NULL이면 검사 자체를 건너뛴다(`supabase/schema.sql` 64·73행). **이건 사고가 아니라 선택이므로 코드에 사유를 남길 것** — 표식이 없으면 다음 사람이 "토큰을 안 싣는 버그"로 읽고 켠다. 나중에 켜기로 하면 2대 허용(토큰 배열)으로 스키마를 바꿔야 한다.

**키에 개인정보를 넣지 않는다.** `key_label`은 내부 식별용이며 이메일·회사명을 강제하지 않는다. 클라이언트가 보내는 것은 키 해시뿐이고, **CSV와 분석 데이터는 종전대로 서버에 가지 않는다**(§2.2). 검증 결과는 store에 `entitlement: {plan, validUntil}`로만 남긴다.

**`service_role` key는 어떤 경우에도 클라이언트·저장소·문서에 두지 않는다**(§2.3). 앱이 쓰는 것은 `anon` public key뿐이며, RLS 전면 차단 + RPC 단일 노출 설계라 이것으로 충분하다. 키 발급·연장·회수는 Supabase 대시보드 SQL Editor에서 사람이 직접 한다.

**여전히 DRM이 아니다.** 응답을 조작하면 통과한다 — 어느 방식이든 같다. 화면 카피에 보안을 주장하지 말 것.

**만료를 기습으로 만들지 않는다.** 만료 7일 전부터 남은 기간을 표시한다. 만료 후에도 **기존 프로젝트는 읽기·내보내기가 열려 있다**(P3의 회수 금지와 동일) — 새로 만들기와 유료 기능만 잠긴다. 만료를 이유로 데이터를 지우지 않는다(90일 만료는 그와 별개의 기존 규칙이다).

전달은 수동(계좌이체/인보이스 → 키 발급). PG 연동은 이 단계에 없다.

**문서 정합**: 채택하면 `AGENTS.md` §3의 "Supabase 미사용" 서술과 `supabase/SETUP.md`를 같은 PR에서 갱신한다. 틀린 규칙은 없는 규칙보다 해롭다(§15).

#### 4-2. 유료 범위 (확정: 무제한 + 일괄 보고서 + 브랜딩)

| 기능 | 무료 | 유료 |
|---|---|---|
| 분석 도구 전체 | ✓ | ✓ |
| 프로젝트 | 1개 | 무제한 |
| **단일 프로젝트 주간 보고서** | **✓ (기존 그대로)** | ✓ |
| 여러 프로젝트 일괄 보고서 | — | ✓ |
| 보고서 브랜딩(로고·회사명·푸터) | — | ✓ |

**기존 무료 기능을 회수하지 않는다.** #812·#825에서 이미 배포된 단일 프로젝트 보고서는 무료로 남는다. 유료는 **새로 만드는 것**(일괄·브랜딩)뿐이다. 이 경계를 코드 한 곳(entitlement 판정)에서 소유하고 화면들이 파생하게 할 것 — 게이트를 화면마다 새로 적으면 다음 기능에서 어긋난다(§7).

**브랜딩 자산도 서버로 가지 않는다.** 로고는 IndexedDB에 data URI로 저장하고 업로드 엔드포인트를 만들지 않는다(§2.2). 용량 상한과 이미지 타입 화이트리스트를 두고, `/storage` 삭제 화면의 대상에 함께 넣을 것 — 지우는 화면에서 빠지면 "지웠는데 남아 있는" 자산이 된다.

**일괄 보고서는 P2 보관함에서 파생한다.** 프로젝트 목록을 두 번째로 나열하지 말고 같은 SSOT를 읽을 것. 관측이 없는 프로젝트는 보고서에서 **빈 값으로 남기고 추정하지 않는다**(§8).

### P5 — 코드 밖 선행조건

돈을 실제로 받기 전에 필요한 것. **수동 키·계좌이체라 PG는 없어도 되지만 아래는 면제되지 않는다.**

- 사업자 등록 · 통신판매업 신고
- 이용약관 · **환불 정책**(전자상거래법 청약철회)
- 개인정보처리방침 갱신 — 결제·인보이스로 수집하는 항목 명시. **CSV는 계속 브라우저에만 있고 서버로 가지 않는다는 기존 문장은 그대로 유지된다**(수동 키 구조라 실제로 참이다).
- 파일럿: 5~10명 4주. 측정 지점은 2주차 업로드 → 지난 결정 검토 → 보고서 활용 → 실제 결제.
- **가격 수용도는 별도 질문으로 측정한다.** 게이트에 금액이 없으므로(§3-4) 클릭 수만으로는 29,000원 가설이 검증되지 않는다. 파일럿 참가자에게 직접 묻는 절차를 파일럿 설계에 넣을 것.
- **키 발급 대장** — 누구에게·언제·만료일. 1개월 기간제라 매달 갱신 대상이 나온다(P4-1).

`lib/brandFacts.js`의 "무료·가입 없음" 문장은 P3~P4에서 **한정 표현으로 바뀌어야 한다**(분석 도구는 계속 무료·가입 없음 / 프로젝트 2개 이상은 유료). SSOT를 먼저 고치고 코드가 그 사본을 따르게 할 것(§2.12).

## 3. 확정된 결정 (2026-09-09)

| # | 항목 | 확정 | 이 결정이 만드는 것 |
|---|---|---|---|
| 1 | 무료 한도 | **프로젝트 1개** | 두 번째 프로젝트 시도가 곧 게이트. 신호가 가장 빨리·많이 나온다 |
| 2 | 키 유효기간 | **1개월 기간제** | 반복 매출이 생기는 대신 **월 단위 수동 재발급 운영**이 필수가 된다 |
| 3 | 유료 범위 | **무제한 + 일괄 보고서 + 브랜딩** | P4가 커진다(키만이 아니라 기능 2개). 기존 단일 보고서는 무료 유지 |
| 4 | 가격 표기 | **금액 미노출, 관심만** | 신호량↑·정확도↓. 가격 검증은 파일럿 인터뷰로 분리 |
| 5 | 키 검증 방식 | **Supabase RPC**(오프라인 서명 폐기) | 월 갱신이 UPDATE 한 줄. **회수 가능**해진다. 대신 grace 캐시가 필수 |
| 6 | 기기 바인딩 | **OFF** | 2대 쓰는 마케터의 마찰 제거. 공유 방지는 파일럿 범위 밖 |

**이 조합에서 특히 조심할 것 두 가지.**

- **2번(기간제)의 부담은 5번이 대부분 없앤다.** 월 재발급·전달이 아니라 만료일 UPDATE 한 줄이 되고, 발급 대장은 테이블 자체가 된다. 남는 것은 **검증이 네트워크에 의존하게 된다는 점**뿐이고, 이건 grace 캐시로 막는다(P4-1).
- **4번(금액 미노출) 때문에 게이트 클릭은 지불 의향이 아니다.** 이 둘을 같은 지표로 읽으면 P5에서 잘못된 결론이 나온다 — 문서 전체에서 두 측정을 분리해 뒀다.

## 4. 단계별 검증

공통: `npm run test:all` · `npm run lint` · `npm run build` · 변경이 화면 배선이면 `npm run test:e2e`.

- **P0** 데모/실데이터 각각의 이벤트 발화 여부. 파라미터 계약 골든.
- **P1** 구 단일 프로젝트 → 신 구조 마이그레이션 골든. 프로젝트 2개에서 스냅샷·결정이 섞이지 않는지 재현. 90일 만료 시 고아 데이터 0.
- **P2** 검토 기한 정렬, 빈 상태(스냅샷 없음)에서 날짜를 지어내지 않음. KO/EN. 라이트 대비.
- **P3** 게이트가 **생성 진입점에서만** 열리고 기존 데이터 접근은 안 막히는지. `source`별 이벤트 구분.
- **P4** 키 4경로: 유효 / 없는 키 / **만료** / **`revoked`**. 만료 7일 전 예고 표시.
  **네트워크 차단 상태에서 grace 캐시로 계속 열리는지**(가장 중요한 회귀 — 여기가 "돈 냈는데 안 열림" 사고 지점). 캐시까지 만료되면 잠기는지.
  만료 후에도 기존 프로젝트 읽기·내보내기가 열려 있는지. 무료 사용자의 **단일 보고서가 그대로 동작**하는지(회수 없음).
  RPC 요청 본문에 **키 해시 외에 아무것도 실리지 않는지**(CSV·파일명·프로젝트명 0). 브랜딩 로고가 `/storage` 삭제 대상에 포함되는지.

미실측으로 남는 것: 실기기, Lighthouse, **실제 지불 의향과 전환율**. 브라우저 검증 통과를 매출 개선으로 주장하지 않는다.
