# Gondry용 NICEPAY 도입 절차

2026-09-19 공식 안내와 현재 코드를 대조했다. **개발 준비와 계약·심사·운영 개통은 별도다.** 현재는 코드 구현 및 로컬 검증 단계이며 신청 상태·계약·발급 키·실결제 결과는 미확인이다.

## 1. 신청할 서비스와 전달할 설명

현재 제품 계약 기준:

| 항목 | 신청·심사에 전달할 내용 |
|---|---|
| 사이트 | https://growthoptplaybook.com |
| 상호 | 공드리공작소 — 기존 사용자 제공 정보 기준 |
| 상품 | Growth Opt Playbook Pro 1개월 이용권 |
| 가격 | 5,900원, 현재 사이트 표시 가격 |
| 제공 기능 | 프로젝트·결정 저장, 보고서 다운로드, 여러 프로젝트 및 브랜딩 |
| 무료 범위 | 분석 기능은 무료 |
| 결제 형태 | 고객이 매번 구매하는 카드 일회 결제. 자동 갱신·빌링 아님 |
| 제공 시점 | 서버에서 결제 승인 확인 후 계정에 이용권 반영 |
| 이용기간 | 승인 시점부터 1개월. 기간 합산은 기존 이용권 정책 적용 |
| 연동 요청 | JS SDK / Server 승인 / Basic 인증 / 자체 개발 사이트 |
| 초기 결제수단 | 카드. 계좌이체·가상계좌·간편결제 추가는 별도 계약·개발 확인 필요 |

Toss 계약이나 카드사 심사가 NICEPAY로 자동 승계된다고 가정하지 않는다. **기존 Toss를 해지하기 전에 NICEPAY 개통과 기존 거래 환불·조회 가능 기간부터 확인**한다.

담당자에게 전달할 문의문:

> 자체 개발한 https://growthoptplaybook.com 에서 마케팅 분석 도구의 Pro 1개월 이용권을 5,900원에 판매하려고 합니다. 분석은 무료이며 유료 기능은 프로젝트·결정 저장과 보고서 다운로드 등입니다. 자동 갱신 없는 카드 일회 결제로 시작하고, JS SDK의 Server 승인·Basic 인증 방식으로 연동하고 싶습니다. 해당 업종의 계약 가능 여부, 신청 채널, 테스트 상점 및 운영 키 발급 방법, 카드사 심사 요건, 등록비·수수료·정산주기·보증보험 조건, 심사용 계정과 결제창 확인 방법을 안내해 주세요. 기존 Toss 연동에서 전환하는 경우 추가로 필요한 절차도 확인 부탁드립니다.

이 문의문은 **작성만 했으며 발송하지 않았다.**

## 2. 가입·상담·계약 — Gondry가 진행

1. [서비스 신청](https://www.nicepay.co.kr/apply/request/econt/request.do)에서 자체 개발 사이트의 전자결제 도입을 신청한다. 개발 계정은 [NICEPAY 시작하기](https://start.nicepay.co.kr/merchant/login/main.do) 경로도 있으며, 신청 담당자에게 위 승인 모델과 연결되는 계약인지 먼저 확인한다.
2. 상품 종류·매출 예상·환불 방식·정산 조건을 전달하고 계약 가능 여부를 확인한다.
3. 계약서 및 구비서류를 NICEPAY의 공식 접수 경로로 제출한다. 신분증·통장·인감 서류는 채팅이나 저장소에 넣지 않는다.
4. 안내받은 등록비와 보증보험 조건을 확인하고 계약을 진행한다.
5. 카드사 등록·심사 완료 및 실제로 사용 가능한 카드사를 확인한다. 완료 예상일은 담당자에게 받아야 하며 임의로 ‘며칠이면 된다’고 확정할 수 없다.

공식 기본 순서는 신청 → 등록비 → 보증보험 → 카드사 등록 → 이용 가능이다. 상담 전화는 1661-7335, 평일 09–17시로 안내되어 있다. [이용절차](https://www.nicepay.co.kr/apply/guide/process.do)

**준비 서류:** 개인사업자는 계약서·고객거래확인, 사업자등록증, 대표자 신분증, 개인인감증명, 정산계좌, 보증보험증권이 안내되어 있다. 법인은 법인인감·등기부·실제소유자 확인·주주명부 등이 추가된다. 실제 제출·면제 범위는 계약 채널 담당자에게 확정받는다. [공식 구비서류](https://www.nicepay.co.kr/apply/guide/document.do)

**공개 요금 참고:** 일반 홈페이지에는 베이직 등록비 33만원(VAT 포함), 카드 3.5%(VAT 별도), 정산 D+7영업일이 표시되어 있다. 이것은 우리 계약의 확정 견적이 아니다. 제휴·업종·계약 조건에 따른 적용 요금, 보증보험료, 면제 여부를 서면으로 확인한다. [공식 요금](https://www.nicepay.co.kr/apply/guide/fee.do)

## 3. 심사할 사이트 준비 — 코드 준비 + 사업자 확인

| 확인할 항목 | 현재 상태 / 다음 행동 |
|---|---|
| 상품·가격·기간·자동 갱신 없음 | 기존 KR/EN 구독 페이지에 표시. 5,900원/1개월 정책 유지 |
| 판매자 정보 | 사용자 제공 상호·대표자·사업자번호·주소·전화·이메일이 코드에 있음. 사업자 서류와 최종 대조 필요 |
| 통신판매업 신고번호 | **미제공**. 신고 여부·번호 또는 적용 상태를 Gondry가 확인해야 함. 임의 생성·면제 판단하지 않음 |
| 이용약관·개인정보처리방침 | 기존 페이지 존재. 이번 변경에 선택 PG가 NICEPAY일 수 있다는 KR/EN 안내 반영 |
| 환불정책 | 기존 사용자 확정 정책: 7일 이내 사용 여부 무관 전액, 이후 미사용 기간 일할 환불, 위약금/수수료 차감 없음. 요청 후 3영업일 이내 처리 |
| 심사 계정 | 기존 이메일·비밀번호 로그인 지원 코드가 있음. 담당자가 요구할 때 제한된 심사용 계정을 준비하고 비밀 경로로 전달 |
| 결제창 확인 | 기존 익명 심사용 위젯은 Toss용. NICEPAY 담당자가 요구하는 심사 방식은 미확인. 해당 위젯을 NICEPAY 심사 완료 증거로 쓰지 않음 |
| 구매 실패 안내·모바일 복귀 | KR/EN 코드 및 모의 화면 테스트. 실제 카드사 앱 복귀는 실기기 검증 필요 |

환불 계산·권리의 법적 적합성을 이 문서로 확정하는 것은 아니다. 위 내용은 이미 사용자와 확정한 제품 정책을 그대로 전달하는 것이다.

## 4. 테스트 상점과 키 — Gondry가 발급, 개발 환경에 직접 설정

회원가입 후 테스트 상점을 만들고 개발정보에서 키를 확인할 수 있다. **Server 승인용 Client key + Basic 인증용 Secret key**인지 확인한다. 구형 MID/merchantKey나 Client 승인/Bearer 방식이면 현재 구현에 그대로 넣을 수 없다. [키·승인 모델](https://github.com/nicepayments/nicepay-manual/blob/main/common/api.md)

샌드박스는 실제 과금이 없으며 테스트 키와 운영 키가 다르다. 샌드박스의 부분 취소에는 제약이 있어 모의 테스트 통과만으로 실환경 부분 환불이 검증되었다고 보지 않는다. [샌드박스 안내](https://github.com/nicepayments/nicepay-manual/blob/main/common/test.md)

| 설정 | 테스트 | 운영 |
|---|---|---|
| `PAYMENTS_PROVIDER` | `nicepay` | `nicepay` |
| `NICEPAY_APPROVAL_MODEL` | `server-basic` | `server-basic` |
| `NICEPAY_MODE` | `test` | `live` |
| `NICEPAY_CLIENT_KEY` / `NICEPAY_SECRET_KEY` | 같은 테스트 상점의 키 | 같은 운영 상점의 키 |
| `PAYMENTS_LIVE_ENABLED` | `false` | 개통 검증 때만 `true` |
| `PAYMENTS_DATABASE_URL` | 분리한 테스트 DB | 기존 운영 결제 DB |
| 서버 API 주소 | `sandbox-api.nicepay.co.kr` | `api.nicepay.co.kr` |

키는 배포 환경 비밀값으로 넣고 소스·문서·스크린샷에 남기지 않는다. 주문의 테스트/운영 구분과 설정이 다르면 코드는 거래 조회를 거절한다. 현재 정책상 `NODE_ENV=production`에서는 테스트 구매를 막으므로, 샌드박스는 별도 로컬 개발 환경에서 검증한다. **운영 설정을 테스트로 바꿔 고객 결제를 검증하지 않는다.**

## 5. 배포·관리자 설정 — 개발 작업

1. 이 작업의 변경을 검토 후 커밋·push·PR로 main에 반영한다. main 직접 push는 하지 않는다. 현재는 미커밋·미배포다.
2. 운영 DB 백업 및 `scripts/payment-periods.sql`의 `provider` 추가를 확인한다. 기존 주문은 Toss로 유지한다. 시작 전 migration 스크립트에 포함돼 있으므로 배포 로그에서 성공을 확인한다.
3. 테스트→운영 키·모드 변경과 DB 변경 순서를 점검하고 초기에는 실구매를 닫은 채 상태를 확인한다.
4. NICEPAY에 서비스 도메인과 필요한 URL을 등록한다.

| 용도 | 운영 주소 |
|---|---|
| 상품·구매 | https://growthoptplaybook.com/subscription |
| 환불정책 | https://growthoptplaybook.com/subscription#refund-policy |
| 인증 결과 반환 | https://growthoptplaybook.com/api/payments/nicepay/return?locale=ko |
| 영어 인증 반환 | https://growthoptplaybook.com/api/payments/nicepay/return?locale=en |
| 승인·취소 웹훅 | https://growthoptplaybook.com/api/payments/nicepay/webhook |

반환은 POST로 받아 서명을 검사하고, 로그인한 주문 소유자의 동일 출처 요청에서 승인한다. 웹훅은 수신 본문을 믿고 이용권을 주지 않고 NICEPAY 거래를 재조회하며 성공하면 평문 `OK`를 돌려준다.

관리자의 개발정보에서 웹훅을 추가하고 테스트 호출·로그·재전송을 확인한다. IP 접근 제한을 쓰려면 Railway 서버의 실제 고정 송신 IP 제공 여부부터 확인한다. 확인되지 않은 IP를 등록해 결제를 막지 않는다. [관리자 설정](https://start.nicepay.co.kr/manual/admin/developers/info.do), [네트워크·시간 초과](https://github.com/nicepayments/nicepay-manual/blob/main/common/preparations.md)

## 6. 개통 전 통과해야 할 테스트

| 테스트 | 합격 조건 | 현재 증거 |
|---|---|---|
| 승인·소유권·금액·서명 | 본인 주문의 정확한 금액·서명만 승인 | 로컬 모의 테스트 |
| 인증 실패·고객 취소 | 이용권과 `purchase` 미발급 | 로컬 분기 테스트, 실제 PG 미검증 |
| 중복 반환·재시도 | 같은 주문의 승인 POST를 반복하지 않음 | 로컬 모의 테스트 |
| 응답 유실·시간 초과 | 망취소 시도, 불확실한 결제는 자동 지급하지 않음 | 로컬 모의 테스트 |
| 웹훅 승인·취소·부분 취소 | PG 조회와 이용권 상태 일치, 성공 응답 `OK` | 서버 모의 테스트, 외부 수신 미검증 |
| 이용권 복원·기간 합산 | 기존 Toss와 신규 NICEPAY 각각 원 PG 조회 | 로컬 회귀 테스트 |
| 데스크톱·iOS·Android | 카드사 인증 후 원 사이트 복귀·구매 결과 확인 | 실제 카드사 앱/기기 미검증 |
| 실제 결제·환불 | PG 관리자 금액/취소와 DB 이용권 대조 | **미실행, 실제 카드 소유자 진행 필요** |
| GA | 신규 실거래 `purchase` 1건·실제 리뷰 저장 1건 대조 | 주요 이벤트 등록됨, 운영 최종 수신 미검증 |

실거래는 현재 5,900원 상품으로 수행한다. 테스트 편의를 위해 운영 상품 금액을 임의로 바꾸지 않는다. 실결제 후 전액 환불, 필요 시 담당자와 부분 환불을 확인한다. 테스트 기록에는 거래 식별자·금액·상태·시각만 남기고 카드번호·키는 넣지 않는다.

## 7. 개통 후 운영과 되돌리기

- 결제 원장은 PG와 DB다. GA 누락만으로 미결제라고 판단하지 않는다.
- 승인 불확실 주문은 관리자 거래 조회로 먼저 확인하고, 사용자에게 곧바로 재결제를 시키지 않는다.
- 환불은 해당 거래의 PG 관리자에서 처리하고 웹훅·조회로 이용권 회수를 대조한다.
- 신규 결제에 문제가 있으면 `PAYMENTS_LIVE_ENABLED=false`로 신규 구매를 닫고 원인을 확인한다. 이때도 계정 이용권/취소 정합성을 별도로 점검한다.
- Toss로 되돌릴 때는 신규 주문의 `PAYMENTS_PROVIDER`를 바꾸며 기존 NICEPAY 주문을 Toss 주문으로 바꾸지 않는다. 양쪽 거래가 남아 있는 동안 양쪽 키와 웹훅 설정을 유지한다.

## 지금 Gondry가 가져오면 되는 것

1. 신청 단계: 신청 전 / 계약·심사 중 / 키 발급 완료 중 어디인지.
2. 담당자가 확정한 승인 모델과 인증 방식. 키 원문은 필요 없다.
3. 적용 견적·정산·보증보험·심사 요구사항.
4. 통신판매업 신고번호 또는 현재 처리 상태.
5. 계약·심사 완료 후 실제 카드 테스트를 진행할 수 있는 시점.

키 입력·계약 제출·실결제·배포가 확인되지 않은 항목을 완료로 표시하지 않는다. 기술 상세는 [개발 전환 문서](nicepay-migration-2026-09-19.md)를 따른다.
