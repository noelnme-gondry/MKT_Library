# 보고서 이용권 결제 운영

5,900원 · 결제일부터 달력 기준 1개월 · 자동 갱신 없음. 기존 유효 이용권은 중복 구매를 막는다. 월말은 다음 달 마지막 날짜로 맞춘다.

## 서버 설정

### Railway 적용 순서

1. 현재 앱과 **같은 프로젝트·환경**에 PostgreSQL 서비스를 추가한다. 앱 서비스 Root Directory는 `v2-migration` 그대로 둔다.
2. 앱 서비스의 **Variables**에 아래 네 변수를 추가한다. DB 서비스에만 추가하면 Next.js 서버가 읽지 못한다.
3. `PAYMENTS_DATABASE_URL`은 PostgreSQL 서비스의 `DATABASE_URL`을 참조하는 변수로 연결한다. 서비스 이름이 `Postgres`라면 `${{Postgres.DATABASE_URL}}`이다. 실제 서비스 이름에 맞추며, 브라우저 코드용 `NEXT_PUBLIC_` 접두사를 붙이지 않는다.
4. PostgreSQL 연결 도구에서 저장소 루트 `scripts/payments-schema.sql`을 한 번 실행한다. 앱 Root Directory 밖의 파일이므로 앱 시작 시 자동 실행되지 않는다. `gop_payment_orders` 테이블이 생성됐는지 확인한다.
5. 테스트 키 검증은 운영 데이터와 분리한 개발 환경에서 진행한다. 현재 코드는 `NODE_ENV=production`에서 테스트 키 결제를 차단하므로, Railway 운영 배포에 테스트 키와 `PAYMENTS_LIVE_ENABLED=false`를 넣으면 `/api/payments/config`는 `enabled:false`, `mode:test`를 반환한다. 운영 환경을 개발 모드로 바꿔 이 차단을 우회하지 않는다. 개발 환경의 `enabled:true`도 설정 형식 확인일 뿐 DB 연결·승인 성공 증명은 아니다.
6. 계정 로그인과 별도 테스트 DB가 준비된 개발 환경의 `/subscription#purchase`에서 토스 테스트 결제 → 새로고침 → 보고서 다운로드 → 복원 코드로 다른 브라우저 복원 → 테스트 취소를 확인한다. Railway PR/staging은 계정 기능이 차단되므로 테스트 키만 복사해도 이 전체 경로를 실행할 수 있는 것은 아니다.
7. 토스 개발자센터의 라이브 결제 상태 변경 웹훅에 `https://growthoptplaybook.com/api/payments/webhook`을 등록한다. 테스트 환경에서도 별도로 등록·검증한다.
8. 테스트와 상점 활성화 확인 후 라이브 키 한 쌍으로 교체하고 `PAYMENTS_LIVE_ENABLED=true`로 재배포한다. 테스트 키를 넣은 상태에서 플래그만 바꾸면 실제 결제가 되지 않는다.

운영자가 입력할 값은 **토스 키 2개·DB 참조 1개·활성화 플래그 1개**다. 5,900원 가격과 판매자 정보는 코드에서 관리하므로 별도 가격·주소 환경변수는 필요 없다. 이 결제 경로에는 Supabase 설정이 필요하지 않다. CSV 저장을 위한 DB도 만들지 않는다.

Railway 앱 서비스의 서버 환경변수에 다음을 설정한다. 소스·문서·채팅에 키 값이나 DB 연결문자열을 붙이지 않는다.

| 변수 | 의미 |
|---|---|
| `TOSS_CLIENT_KEY` | 토스 주문서형/결제창형 연동 클라이언트 키 (`test_gck_` / `live_gck_`) |
| `TOSS_SECRET_KEY` | 같은 상점·환경의 시크릿 키 (`test_gsk_` / `live_gsk_`) |
| `PAYMENTS_DATABASE_URL` | 결제 주문만 보관하는 PostgreSQL 연결문자열 |
| `PAYMENTS_LIVE_ENABLED` | 실결제 활성화 시에만 `true`. 테스트 완료 전에는 설정하지 않는다. |

테스트 키와 라이브 키를 섞지 않는다. API 개별 연동 키(`ck`/`sk`)와 신규 주문서 연동 키는 다른 제품이므로 SDK만 임의로 바꾸지 않는다. 토스 개발자센터에서 주문서형/결제창형 키를 확인한다.

먼저 해당 DB에 `scripts/payments-schema.sql`을 적용한다. DB 사용자에게 이 테이블의 조회·삽입·갱신 권한을 부여한다. DB 연결은 서버에만 제공한다. `/api/payments/config`에는 사용 가능 여부와 공개 클라이언트 키만 반환된다. 설정 미완료 시 결제 UI는 구매 문의를 안내한다.

## 결제와 복원

1. 서버가 주문번호·5,900원·상품 버전·복원 코드 해시·멱등 키를 저장한다.
2. 사용자 클릭 후에만 토스 SDK를 불러온다. 카드 입력은 토스 화면에서 처리한다.
3. 리턴 경로는 `/api/payments/return`이다. 결제키·주문번호는 HttpOnly 임시 쿠키로 옮기고, 추적 스크립트가 있는 구독 페이지에 도달하기 전에 URL에서 제거한다.
4. 서버는 주문 소유 쿠키·금액·토스 응답을 확인한 뒤 승인 결과와 만료일을 저장한다. 동일 주문의 재시도에는 같은 멱등 키를 사용한다. 승인 결과가 불명확하면 재결제하지 않고 승인 확인을 재시도한다.
5. 활성화 후 복원 코드를 파일로 보관할 수 있다. 다른 기기의 구독 페이지에서 이 코드로 이용권을 복원한다. 프로젝트 파일은 별도 백업/가져오기로 이동한다.
6. 이용권 검증 장애 시 마지막 유효 캐시는 최대 72시간이며 원래 만료일을 넘지 않는다. 검증 성공 시 취소·만료가 확인되면 권한을 회수한다. 이것은 브라우저 내 기능 제한이며 DRM을 보장하지 않는다.

CSV·분석 결과·프로젝트명·파일명·로고는 주문·승인·복원 요청에 포함하지 않는다. 결제 복원 코드를 GA나 고객지원 공개 로그에 남기지 않는다.

## 환불과 취소

공개 정책은 `/subscription#refund-policy` 및 `/en/subscription#refund-policy`가 안내한다. 환불 접수 후 운영자가 토스 상점관리자에서 해당 주문의 전액/부분 취소를 처리한다. 앱에 비밀키를 입력하는 관리자 화면은 만들지 않는다.

토스 결제 상태 변경 웹훅 주소는 `https://growthoptplaybook.com/api/payments/webhook`이다. 웹훅 본문을 신뢰하지 않고 토스 API로 해당 결제를 조회해 취소를 반영한다. 웹훅이 누락돼도 다음 이용권 확인에서 토스 상태를 다시 조회한다. 부분 취소도 공개 환불정책에 따라 유료 이용을 종료한다. 이미 저장한 프로젝트 읽기와 백업은 막지 않는다.

결제·공급 기록은 법정 5년 보관 대상이다. DB 백업·법정 보관기간 이후 파기 운영은 실결제 개시 전에 설정해야 한다. 승인되지 않은 주문과 실제 거래 기록을 구분하며, 승인 결과가 불명확한 주문을 임의 삭제하지 않는다. [전자상거래법 시행령 제6조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1018638379)

## 배포 후 필수 실측

- 실제 상점의 테스트 결제 → 승인 → 새로고침 → Word/Excel 다운로드 → 다른 브라우저에서 코드 복원.
- 토스 테스트 취소 → 웹훅 또는 접근 재검증 → 다운로드 제한, 프로젝트 백업 유지.
- 중간 네트워크 끊김 → 동일 주문 승인 재시도; 이중 결제 없음.
- 라이브 상점 활성화, 사업자 표시 정보·연락처·통신판매업 신고 적용 여부 확인.
- 테스트 이벤트 `state=test`를 매출로 집계하지 않는다. `payment_access_activated`는 클라이언트 활성화 이벤트로, 회계 매출의 정본은 토스/주문 DB다.

현재 자동 검증은 모의 토스 응답과 DB 테스트 대역을 사용한다. 실제 토스·PostgreSQL·웹훅·라이브 결제는 환경 설정 후 별도 실측해야 한다.

공식 연동 근거: [SDK 초기화](https://docs.tosspayments.com/sdk/v2/js/environment), [API 키 종류](https://docs.tosspayments.com/reference/using-api/api-keys), [금액 검증과 승인 흐름](https://docs.tosspayments.com/guides/v2/get-started/payment-flow), [Railway 서비스 변수 참조](https://docs.railway.com/integrations/api/manage-variables).

## 토스 상점 심사 보완

2026-09-14 사용자 제공 보완 요청의 실제 상태와 제출 전 확인 항목은 [상점 심사 보완 기록](toss-review-readiness-2026-09-14.md)을 따른다. 공개 페이지의 사업자 표시, 심사자의 로그인 가능 여부, 실제 결제창 진입은 별개로 검증한다. 테스트 결제 차단을 해제하거나 구매 이용권을 임의 발급한 것으로 심사 대응을 대신하지 않는다.

운영 환경에 `test_gck_` 클라이언트 키가 있으면 구독 페이지의 **심사용 테스트 결제창**에서 로그인 없이 신형 위젯과 선택 결제수단의 창을 확인할 수 있다. `/api/payments/config`의 `reviewClientKey`는 공개 테스트 키만 반환하며, 실제 구매 `enabled:false`는 유지한다. 이 경로는 테스트 창 확인 전용으로 승인·이용권 발급을 하지 않으므로 위의 전체 결제 검증을 대체하지 않는다.

### 심사용 아이디·비밀번호 계정 발급

카드사 심사가 소셜 로그인 대신 일반 아이디·비밀번호를 요구할 때만 연다. **새 데이터베이스를 만들지 않는다** — 계정 테이블은 결제와 같은 PostgreSQL 서비스(`PAYMENTS_DATABASE_URL`)에 있다. 순서를 지킨다. 1번 배포가 끝나기 전에 2번을 실행하면 `password_hash` 컬럼이 없어 실패한다.

1. **배포한다.** 앱 시작 시 `scripts/payment-periods.sql`이 자동 실행되어 `gop_accounts`에 `password_hash`를 추가하고 `google_sub`의 NOT NULL을 푼다. 멱등이라 재배포해도 안전하다.
2. **계정을 만든다.** 아래는 **환경변수가 아니라 한 번 실행하는 명령**이다. Variables 탭에 붙여넣지 않는다. 비밀번호는 12자 이상이어야 하고, 두 값은 이 명령에만 쓰고 어디에도 저장하지 않는다. 둘 중 편한 쪽을 쓴다.

   **(가) DB 콘솔에 SQL 붙여넣기 — 앱 서비스에 터미널을 열 수 없을 때.** 연결문자열 없이 로컬에서 실행하면 계정을 만들 SQL을 `v2-migration/review-account.sql`에 쓴다(소유자 전용 권한, `.gitignore` 대상). 그 파일을 열어 Railway PostgreSQL 서비스의 쿼리 화면에 붙여넣고 **실행 후 파일을 삭제한다** — 비밀번호 검증값이 들어 있다. 화면에 바로 출력하지 않는 이유도 같다(터미널 기록·CI 로그에 남는다). 해시는 자기 솔트를 품고 있어 이 경로도 (나)와 같은 결과다.

   ```
   REVIEW_ACCOUNT_EMAIL=<심사용 아이디> REVIEW_ACCOUNT_PASSWORD=<비밀번호> \
     node scripts/provision-review-account.mjs
   ```

   **(나) 스크립트가 직접 쓰기 — 앱 서비스에서 명령을 실행할 수 있을 때.** 같은 명령에 `PAYMENTS_DATABASE_URL`이 있으면 바로 기록한다. 앱 서비스에는 이미 그 변수가 있으므로 다시 넣지 않는다. 로컬에서 실행한다면 PostgreSQL 서비스의 공개 연결문자열을 같은 이름으로 넘긴다.

   아이디는 메일을 보내지 않으므로 실제 메일함이 없어도 되지만, 심사자에게 전달할 값이라 사업자 도메인 주소를 쓴다. 계정은 체험·구매 없이 **무료 상태**로 만들어 심사자가 무료 화면과 구매 유도를 그대로 본다.
3. **로그인을 연다.** 앱 서비스 **Variables**에 `ACCOUNT_PASSWORD_LOGINS`를 그 아이디로 설정하고 재배포한다. `ACCOUNT_ALLOWED_EMAILS`를 이미 쓰고 있다면 같은 아이디를 거기에도 더한다. 두 값 모두 쉼표로 여러 개를 적을 수 있다.
4. **확인한다.** 헤더 마이페이지의 `아이디·비밀번호로 로그인`에서 발급한 값으로 로그인되는지, 로그아웃 후에도 다시 되는지 본다. 그다음 심사 회신에 아이디와 비밀번호를 적는다.
5. **닫는다.** 심사가 끝나면 `ACCOUNT_PASSWORD_LOGINS`를 비우고 재배포한다. 값이 비면 API와 화면의 입력란이 함께 사라진다. 계정 자체를 지우려면 해당 행의 `password_hash`를 `NULL`로 돌린다.

| 값 | 두는 곳 | 성격 |
|---|---|---|
| `REVIEW_ACCOUNT_EMAIL` · `REVIEW_ACCOUNT_PASSWORD` | 2번 명령줄에만 | 1회성. Variables·저장소·문서에 남기지 않는다 |
| `ACCOUNT_PASSWORD_LOGINS` | 앱 서비스 Variables | 심사 기간 동안만 |
| `PAYMENTS_DATABASE_URL` | 앱 서비스 Variables | 이미 있는 값을 그대로 쓴다 |

비밀번호는 scrypt로만 저장하므로 발급 후에는 어디에서도 다시 읽을 수 없다. 분실하면 2번을 다시 실행해 덮어쓴다. 이 경로는 지정된 아이디에만 열리는 심사용이며 공개 비밀번호 회원가입이 아니다 — `docs/product-ssot.md` F-02의 "분석은 가입·로그인 없이"는 그대로다.
