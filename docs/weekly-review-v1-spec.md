### 1.1 결정 이력은 어디로 가나

별도 페이지로서의 결정 검토함은 없앤다. 대신 **Weekly Review 안의 접기 섹션**으로 흡수한다.

```
── LAST DECISION ──────────────────
  Meta AAP 예산 +15%  목표 방향 변화·가드레일 충족
  ...

  ▸ 지난 결정 전체 보기 (12건)      ← 접힘. 펴면 이력 표 + CSV 내보내기
───────────────────────────────────
```

이유는 P2다. 결정 이력은 **매주 보는 것이 아니라 가끔 되돌아보는 것**이라 상시 목적지를 차지할
필요가 없다. 기존 화면의 기능(이력 표 · 상태 필터 · CSV/ICS 내보내기 · 지난 발견 목록)은
그대로 옮기고 진입점만 접기로 바꾼다. **기능을 지우는 게 아니라 위계를 내린다.**

`components/WeeklyReview.jsx`(697줄)의 로직은 대부분 재사용된다 —
`decisionReview`·`forecastReview`·`rankFindings`·`detectFindingConflicts` 호출부는 유지하고
셸과 라우트만 없앤다.

### 1.2 옛 화면 사용자 안내 — 도치 1회

같은 URL의 의미가 바뀌므로, 이전에 결정 검토함을 쓴 흔적(저장된 결정 ≥ 1건)이 있는 사용자에게
**도치가 첫 진입 1회** 말을 건다. 흔적이 없으면 띄우지 않는다(새 사용자에게 없어진 화면을
설명하는 건 소음이다).

```
   ( 도치 )   결정 검토함이 여기로 들어왔어요.

   이제 매주 데이터를 올리면 지난 결정의 결과까지 한 번에 확인할 수 있어요.
   지금까지 저장한 결정 12건은 그대로 있습니다.

   [ 지난 결정 보기 ]   [ 알겠어요 ]
```

- 노출 판정은 기존 도치 온보딩과 같은 규칙: 영구 끄기는 `localStorage`, 세션 반복 차단은
  `sessionStorage`. 저장소를 못 쓰면 **노출 쪽으로 폴백**한다.
- `[ 지난 결정 보기 ]`는 §1.1의 접기 섹션을 펼친 상태로 스크롤한다.
- 서버 스냅샷은 항상 "닫힘"이라 프리렌더 HTML에 오버레이가 없다(크롤러가 가려진 화면을 보지 않음).
- 포즈는 `public/assets/dochi/`에 **실재하는 것만** 쓰고 스모크가 단언한다.

### 2.2 기간 판정 — 데이터 최대 날짜의 **요일까지 맞춰** 자른다

원안(§5)은 "지난 완료 주"를 기본으로 잡았는데, 그러면 수요일에 들어온 사람은 월·화·수
데이터를 갖고도 그 주를 통째로 못 본다. 반대로 완료 주를 안 기다리고 그냥 비교하면 부분 주와
전체 주를 견주게 된다. **요일 수를 맞추면 둘 다 해결된다.**

```
maxDate   = 데이터의 최대 date
weekStart = maxDate가 속한 ISO주(월요일 시작)의 월요일
n         = maxDate - weekStart + 1        // 1~7일

current   = [weekStart,      maxDate]
previous  = [weekStart - 7d, maxDate - 7d]  // 같은 요일 수만큼
```

예: 데이터가 이번 주 **수요일**까지면 → `월·화·수` vs `전주 월·화·수`.
7일 다 차 있으면 자연스럽게 완료 주 vs 완료 주가 된다. **분기가 하나도 없다.**

요일 수를 맞추는 게 중요한 이유는 광고 성과에 **요일 효과가 크기** 때문이다. 주말 CPA가 평일과
다른 계정에서 월–수 vs 전주 7일을 비교하면 요일 구성 차이만으로 두 자릿수 변화가 나온다.
같은 요일끼리 맞추면 그 효과가 상쇄된다.

**규칙**
- 주 경계는 **ISO 주(월요일 시작)**. 날짜 문자열은 UTC로 파싱되므로 요일 판정은 `getUTCDay()`
  (`getDay()`는 UTC 이서 타임존에서 하루 밀린다 — 기존 함정).
- 두 기간의 **일수는 항상 같다**(구성상 보장). 다르면 버그이므로 골든으로 단언한다.
- `n < 7`이면 모든 카드 상단에 **부분 주 배지**를 고정한다: `월–수 (3일) · 전주 같은 요일과 비교`.
- `n <= 2`면 표본이 작아 판정이 흔들린다. 계산은 하되 배지를 경고 톤으로 바꾸고
  §4.1의 볼륨 게이트를 **2배로** 올린다(전환 30 → 60). 며칠치로 주간 결론을 단정하지 않는다.
- previous 구간에 데이터가 없으면(첫 주) 비교 대신 "비교할 지난 기간이 없습니다"로 정직하게 멈춘다.

### 2.2b 사용자 날짜 필터

자동 판정은 **제안**이고 사용자가 언제든 바꿀 수 있어야 한다. 자동 비교가 틀렸는데 고칠 방법이
없으면 Review 전체를 못 믿는다.

```
비교 기간                                          [ 변경 ]

  이번 기간   2026-08-31 ~ 2026-09-02  (월–수, 3일)
  지난 기간   2026-08-24 ~ 2026-08-26  (월–수, 3일)
```

`[ 변경 ]`을 열면:
- **이번 기간**의 시작·끝을 직접 지정. 바꾸면 **지난 기간이 같은 길이로 자동 재계산**된다.
- 지난 기간도 따로 지정 가능(격주 비교, 캠페인 전후 비교 등).
- 두 기간의 **일수가 달라지면 경고를 띄우되 막지는 않는다**:
  `기간 길이가 다릅니다(7일 vs 3일). 변화율이 기간 차이 때문일 수 있습니다.`
  사용자가 의도적으로 그럴 수 있으므로 결정은 사용자에게 남긴다.
- 프리셋: `최근 7일 vs 직전 7일` · `지난 완료 주 vs 그 전주` · `이번 달 vs 지난 달`

선택한 기간은 프로젝트에 저장되어 다음 Review의 기본값이 된다.

### 2.3 스냅샷 — 무엇을 저장하고, 그래서 사용자가 뭘 덜 하게 되나

**사용자가 겪는 것부터**

| | 스냅샷 없을 때 | 스냅샷 있을 때 |
|---|---|---|
| 매주 올리는 파일 | **2주치** (지난주까지 다시) | **이번 주치만** |
| 컬럼 매핑 | 매번 확인 | 자동 (헤더가 같으면 무음) |
| KPI·목표 | 매번 지정 | 자동 |
| 볼 수 있는 범위 | 2주 비교만 | **8주 추세**, "평소 변동 범위" 판정 |
| 지난 결정 판정 | 그 파일에 있는 기간만 | 결정 시점 전후 자동 조회 |

즉 스냅샷의 값어치는 "저장해준다"가 아니라 **매주 반복하던 세 가지 행동(2주치 뽑기 · 매핑 확인
· KPI 지정)을 없애는 것**이고, 덤으로 §4.1의 변동성 판정이 가능해진다. 2주치만으로는
"이번 주 +8%가 평소 범위인지"를 알 방법이 없다.

**무엇을 저장하나** — 원본 행이 아니라 **주 × 캠페인 집계 한 줄씩**이다.

```
snapshot = {
  periodStart, periodEnd, days,
  rows: [{ channel, campaign, cost, impressions, clicks, installs, actions, revenue }],
  kpi: { metric, value, direction },
  createdAt
}
```

50,000행 원본이 캠페인 수십 개짜리 표 하나로 줄어든다. 8주를 모아도 수백 행이다.
**저장 위치는 기존 IndexedDB 워크스페이스**(`lib/workspace-storage/`) — 브라우저 안이고
서버로 가지 않는다. `/storage`에서 언제든 지울 수 있고 90일 만료도 그대로 적용된다.

**저장하지 않는 것**: 원본 CSV 행, 개별 사용자 식별자, 원본 파일 자체.
캠페인명은 저장된다(그게 없으면 원인을 못 좁힌다) — 이 사실을 저장 안내에 명시한다.

**두 업로드 경로를 모두 지원한다**
- **2주치 업로드** (무상태): 스냅샷이 없어도 첫 방문자가 그 자리에서 Review를 완주한다.
- **이번 주치만 업로드**: 직전 스냅샷을 previous로 쓴다.

전자가 없으면 첫 사용자가 아무것도 못 하고, 후자가 없으면 매주 같은 데이터를 다시 올려야 한다.
둘 다 V1 범위다. **어느 경로인지 화면이 말한다**:
`지난주 데이터는 저장된 기록을 사용합니다 (2026-08-24 ~ 08-30)`

## 4. 카드 1 — SNAPSHOT (무엇이 바뀌었나)

### 4.1 유의미한 변화 판정 — 이 제품의 품질이 갈리는 곳

**단순 WoW %로 경보를 울리면 안 된다.** 세 가지를 함께 본다.

```
significant(metric) =
     |Δ%| >= MIN_PCT                    // 크기
  && |z|  >= MIN_Z                      // 평소 변동성 대비
  && volume >= MIN_VOLUME               // 표본
```

| 상수 | 값 | 근거 |
|---|---|---|
| `MIN_PCT` | 5% | 임시 확인 기준이며 이하는 노이즈라고 확정하지 않음 |
| `MIN_Z` | 1.5 | 최근 8주 주간값의 표준편차 대비 |
| `MIN_VOLUME` | 전환 30건 | 임시 표본 하한, 실제 데이터로 튜닝 필요 |
| `LOOKBACK_WEEKS` | 8 | z 계산용, 스냅샷이 3주 미만이면 z 판정 생략(크기+볼륨만) |

z는 최근 주간값의 **표본 평균·표준편차**로 계산한다. `ANOMALY_MATH.detect`
(`utils/anomalyMath.js:40`)를 재사용하려다 접었다 — 그건 일별 EMA에 요일 보정을 얹은 엔진이라
주간 집계에 맞지 않는다(각 점이 같은 길이의 기간이라 요일 효과가 없고, EMA 분산은 7점에서
안정되지 않는다). 더 중요한 이유는 **화면이 그리는 띠와 판정이 같은 값이어야 한다**는 것이다:
결론 카드가 "평균 ±1σ 밖으로 나갔다"고 말하면서 판정은 EMA를 쓰면 사용자가 그림과 문장의
불일치를 먼저 발견한다. `summarizeBaseline`이 돌려주는 `lo`/`hi`가 곧 화면의 회색 띠다.

**모르는 것을 통과로 세지 않는다.** 이력이 `minBaselineWeeks`(3주) 미만이거나 흩어짐이 0이면
변동성 검사를 **건너뛰고**(`skipped:true`, `pass:false`) 크기·표본만으로 판정하되,
`baselineKnown:false`를 함께 내보내 화면이 "비교 이력이 2주뿐이라 평소 범위를 아직 모릅니다"라고
말하게 한다. 흩어짐 0을 무한대 z로 바꿔 "매우 유의미"로 뒤집지 않는다.

**빈 값을 0으로 읽지 않는다.** `Number(null)`·`Number("")`·`Number(false)`가 전부 0이라
`Number()`를 그대로 쓰면 빈 값이 조용히 0이 된다 — 이력에 0짜리 주가 섞이고, 표본 미지정이
"0건"이 되며, 값 없는 지표가 유효한 0으로 판정을 통과한다. 셋 다 실제로 테스트에 걸렸다.

### 4.2 카피

**유의미할 때**
```
CPA +8.4% 악화
$7.42 → $8.04
전환 +3.1% · 비용 +11.8%
```

**유의미하지 않을 때** (P5)
```
설정한 확인 기준을 넘는 변화가 없습니다.
CPA +0.8% 변화는 최근 8주 변동 범위 안입니다.
```
→ 이 경우 **§5(Why)와 §7(Next Move)을 자동 접는다.** 운영 기준을 넘지 않았기 때문이다. 성과 동등성이나 효과 없음을 뜻하지 않는다고 함께 알린다.

**목표 대비** (target 있을 때만)

## 5. 카드 2 — WHY (원인)

### 5.1 엔진

`PVM_MATH.decomposeFinest(rowsP1, rowsP2, keys)` → `rollup(finest, keyFn, R1, R2)`
(`utils/pvmMath.js:226,395`). 이미 잔차 없는 Bennet 분해이고 mix/rate 항등식이 보장된다.
브리지는 `lib/weekly-review/varianceBridge.js` — **새 수학을 만들지 않고 번역만** 한다.

**번역에서 걸린 것 셋** (전부 실측으로 드러났다):

1. **엔진은 `r.spend`를 읽지 `r.cost`가 아니다.** 스냅샷은 `cost`로 저장하므로 갈아끼워야 한다.
   그냥 넘기면 비용이 전부 0이 되고 분해는 조용히 "전부 효율 변화"라고 답한다. 골든이 소스에서
   번역 존재를 확인하고, 빼면 실제로 실패한다.
2. **`지출>0 · 결과=0` 셀 하나가 분해 전체를 거부시킨다.** `validateAggregateContract`가
   `NOT_IDENTIFIED`를 돌려준다(옳은 판단 — 그 셀의 CPA는 정의되지 않는다). 그런데 실제 주간
   데이터에는 그런 캠페인이 거의 항상 있다. **실측하니 지출 800원짜리 하나가 전체를 막았다.**
   그래서 소액 셀(두 기간 결과 합 < 30)을 `기타(소액)`로 먼저 합친다.
3. **합쳐도 남는 셀은 빼되, 뺀 사실과 금액을 반드시 함께 낸다.** 묶음의 전환이 전부 0이면 여전히
   못 푼다. 검증은 **기간별**이라 "지난주엔 전환이 있었는데 이번 주 0"인 캠페인(정지·소재 소진으로
   흔하다)도 막는다. 아예 못 답하는 것보다 **결과를 낸 캠페인들 안에서** 답하고 범위를 밝히는 편이
   낫다 → `excluded`(뺀 셀·기간별 금액) · `overall`(전체 CPA) · `coversAllSpend`를 함께 돌려주고
   **화면이 반드시 고지한다.** 조용히 빼면 그 순간 거짓 숫자가 된다. `excludeZeroResultCells:false`로
   두면 빼지 않고 거부하는 선택지도 있다.

**비율은 불안정하면 내주지 않는다.** 효율과 믹스가 서로 반대로 커서 ΔCPA가 0에 가까우면
`rate/Δ`가 폭발한다. `|Δ| < 0.5 × (|효율|+|믹스|)`면 `shares:null` + `sharesReason:"offsetting"`을
주고 화면이 금액으로만 말하게 한다.

- `keys` = `[channel, campaign]` (channel 없으면 `[campaign]`)
- 반환 각 원소: `{ mix, rate, contribution, s1, s2, cpa1, cpa2 }`
- **분해는 최소 grain에서 한 번만** 하고 상위는 `rollup`으로 합산한다(단계별 재분해 금지 — 부분합이 안 맞는다).

### 5.2 화면

```
왜 CPA가 올랐나요?              +8.4%

  효율 저하   +6.3%p  (75%)   각 캠페인 자체 성과
  믹스 변화   +2.1%p  (25%)   캠페인별 결과 건수의 비중 변화

→ 예산 믹스보다 캠페인 자체 효율 저하가 더 큰 원인이었습니다.
```

**두 항이 비슷할 때**(각각 총변화의 20% 이상, 기존 `classifyNarrative` 기준과 동일)는
한쪽으로 단정하지 않고 "두 요인이 함께 작용했습니다"로 쓴다.

### 5.3 기여 상위

`|contribution|` 내림차순 상위 3개. **전체가 아니라 3개** (P2).

| 캠페인 | CPA 변화 | 전체 변화 기여 |
|---|---|---|
| Google UAC A | +22% | 48% |
| Meta AAP | +2% | 11% |
| ASA Brand | −7% | −8% |

`[ 더 자세히 보기 ]` → 기존 5-21(성과 변동) 도구로 같은 데이터를 들고 이동.

### 5.4 "비중"은 결과 비중이다

shift-share의 `s`는 비용 비중이 아니라 **결과(전환) 비중**이다. 비용 열 옆에 "비중"이라고
쓰면 비용 비중으로 오독된다 — 라벨을 **"결과 비중"**으로 명시한다. (기존에 실제로 났던 신뢰 사고)

### 5.5 분석 라우터 (P3)

**모든 분석을 돌리지 않는다.** 신호가 있을 때만 해당 분석을 실행하고 카드를 렌더한다.

| 신호 | 조건 | 실행 | V1 |
|---|---|---|---|
| KPI 변화 | `significant(kpi)` | PVM 분해 | ✅ |
| 비용 급변 | `|Δspend| ≥ 15%` | 믹스 강조 | ✅ |
| CTR 하락 + creative 컬럼 | `Δctr ≤ −10%` && creative 매핑됨 | 소재 피로도 | 나중 |
| 세그먼트 급변 | share 변화 ≥ 10%p | 구성 변화 | 나중 |
| 목표 존재 | target 있음 | 페이싱 | 나중 |
| **신호 없음** | — | **아무것도 안 함** | ✅ |

라우터는 `lib/weekly-review/router.js` 순수 함수로 두고 골든으로 고정한다.
**"신호 없음 → 빈 결과"가 정상 경로**이므로 그것도 골든에 넣는다.

**세 가지를 서로 구분해서 내보낸다.** 하나로 뭉치면 화면이 거짓말을 한다.

| 상태 | 뜻 | 화면 |
|---|---|---|
| `quiet` | 평소 범위 안이라 확인할 것이 없다 | "이번 주는 확인할 것이 없습니다" |
| `unknown` | 지표를 잴 수 없어 판정을 못 했다 | "판정할 수 없습니다" + 사유 |
| `signal` | 돌릴 분석이 있다 | 원인·행동 카드를 편다 |

`skipped`의 사유도 넷으로 갈린다: `no_signal`(봤는데 조용함) · `data_missing`(컬럼 없음, 어떤
컬럼인지 함께) · `not_assessable`(값을 못 잼) · `not_in_v1`(의도적 제외, `plannedFor` 포함).

**신호는 평가기와 짝지어 등록한다.** 처음에 조건을 `if`로 늘어놓았더니, 레지스트리에만 올라간
신호가 어느 분기에도 안 걸려 조용히 `no_signal`로 떨어졌다 — **"본 적 없음"이 "없음"으로
둔갑**하는, 이 모듈이 막으려던 바로 그 오류다. 커버리지 가드도 그것을 못 잡았다(신호가
`skipped`에 나타나기는 하니까). 지금은 `EVALUATORS[id]`가 없으면 `not_evaluated`로 남고,
골든이 **켜진 신호마다 평가기 존재**를 강제한다. 신호를 추가할 때 평가기를 빠뜨리면 테스트가 먼저
잡는다.

## 6. 카드 3 — LAST DECISION (지난 결정은 먹혔나)

이 제품의 진짜 차별점. 일반 주간 보고는 `지난주 숫자 vs 이번주 숫자`에서 끝나지만
여기서는 **`지난 결정 vs 실제 결과`**를 본다.

### 6.1 Decision 스키마 확장 (v8 → v9)

현재 `DECISION_REVIEW_SAFE_FIELDS`(`lib/decisionReview.js:9`)에는 `action`이 자유 문자열이고
**guardrail이 없다.** 그래서 자동 판정이 불가능하다. 다음을 추가한다.

| 신규 필드 | 예 | 용도 |
|---|---|---|
| `actionKind` | `increase_budget` \| `decrease_budget` \| `hold` \| `replace` \| `investigate` | 판정 분기 |
| `actionTarget` | `Google UAC A` | 결과 조회 대상 |
| `actionAmount` | `+15%` | 실행 여부 확인 |
| `goalMetric` | `actions` | 성공의 정의 |
| `goalDirection` | `up` | 〃 |
| `guardrailMetric` | `cpa` | 실패의 정의 |
| `guardrailOp` | `lte` | 〃 |
| `guardrailValue` | `8.0` | 〃 |

**마이그레이션**: v8 레코드는 신규 필드가 전부 `null`이다. 이때는 자동 판정을 하지 않고
`판정 불가 — 이 결정에는 목표·가드레일이 기록되지 않았습니다`로 표시한다.
**옛 레코드를 추측으로 채우지 않는다.**

### 6.2 판정 로직

```
if (goal 없음 || guardrail 없음)        → UNSCORED  "판정 불가"
if (대상 데이터 없음)                    → NO_DATA   "대상 캠페인이 이번 주 데이터에 없습니다"
if (실행 안 됨: |actual Δ| < 1/3 예정)   → NOT_APPLIED "결정이 실행되지 않은 것으로 보입니다"

goalMet      = goalDirection 방향으로 significant하게 움직였는가
guardrailMet = guardrail 조건을 만족하는가

goalMet && guardrailMet   → WORKED        목표 방향 변화·가드레일 충족
goalMet && !guardrailMet  → MIXED         △ 목표는 달성, 가드레일 이탈
!goalMet && guardrailMet  → NO_EFFECT     – 뚜렷한 변화 없음
!goalMet && !guardrailMet → BACKFIRED     목표 변화 미확인·가드레일 이탈
```

**`NO_EFFECT`를 "효과 없음"이라고 단정하지 않는다.** 화면 문구는
`뚜렷한 변화를 확인하지 못했습니다 (효과가 없다는 뜻은 아닙니다)`. 1주 표본으로 효과를 부정할
검정력이 없다. 판정 결과에 `meansNoEffect:false`를 함께 실어 보내 화면이 그 뜻을 따르게 하고,
골든이 보고서 문장에 "효과 없음"이 나타나지 않는지 단언한다.

**목표 방향 변화 판정에는 잠정 크기·볼륨 기준을 적용한다(통계적 검정 아님). 가드레일에는 선언한 한계선을 적용한다.** 전환 +0.5%를 "목표 달성"
이라고 부르면 결정 기록 전체가 쓸모없어진다. 반대로 가드레일은 **선언된 한계선**이라 `CPA ≤ $8`을
넘었으면 유의미하든 아니든 넘은 것이다. 두 검사에 같은 잣대를 대면 안 된다.

**목표 방향 `hold`는 사전 동등성 범위가 없으므로 `UNSCORED`로 둔다.** 악화 신호가 없다는 사실만으로 유지·동등성을 입증할 수 없다.

**실행 여부를 먼저 본다.** 예정 변화의 1/3도 안 움직였거나 반대 방향으로 갔으면 `NOT_APPLIED`이고
목표를 **채점하지 않는다**. 표시 문구는 “지출에서 예정 변화 미확인”이며 실제 실행 여부까지 단정하지 않는다.
단, 실행 여부는 `actionAmount`가 퍼센트일 때만 잴 수 있다. `+$5,000` 같은 절대금액은 비율로
읽지 않고(그걸 0.05로 읽으면 판정이 통째로 틀린다) 검사를 건너뛴다.

### 6.3 화면

```
지난주 결정                                     Sep 1
Meta AAP 예산 +15%
목표: 전환 증가 · 가드레일: CPA ≤ $8.00

  전환   +16.8%   ✓ 목표 달성
  CPA    $7.82    ✓ 가드레일 안
  비용   +14.1%   (예정 +15%)

목표 방향 변화·가드레일 충족 — 볼륨이 늘었고 CPA는 목표 안에 유지됐습니다.
```

주간 카드의 실제값은 두 기간의 동일 대상 집계에서 계산한다. 기존 `buildComparableDecisionActual`은 접힌 결정 검토함에서 계속 사용한다. 두 경로를 같은 구현이라고 부르지 않는다. 주간 기록은 기존 comparisonScope에 기준 기간·통화·전환 기준을 보존하고 불일치 시 판정하지 않는다.

첫 사용자(결정 없음)는 이 카드를 **렌더하지 않는다.** 빈 상태를 만들지 않는다.

것은 절 자체가 없어야 한다 — 렌더러도 본문이 빈 절의 제목을 쓰지 않는다.

**초안은 구조화된 데이터이고 문자열 렌더는 따로다.** 통화 표기는 `utils/format.js`가 소유하므로
`renderReportText(draft, format)`이 주입받는다. 보고서가 자기 통화 규칙을 새로 만들면 화면과
보고서의 금액이 갈린다.

## 9. 첫 사용자 경로

지난 결정이 없으므로 카드 3을 건너뛴다.

```
업로드 → 무엇이 바뀌었나 → 왜 → 이번 주 행동 → 보고서 → 결정 저장
                                                            ↓
                              "다음 주에 이 결정의 결과를 확인할 수 있습니다."
```

마지막 문장이 **retention trigger**다. "저장되었습니다"보다 훨씬 강하다.
저장 시 검토일(다음 월요일) `.ics` 다운로드를 제안한다 — 기존 `serializeDecisionReviewIcs`
(`lib/decisionReview.js:156`)가 이미 있다.

### 13.1 나중에 다시 볼 것

- **임계값 튜닝** — 실제 캠페인 데이터로 오탐/미탐을 재본다. 특히 `MIN_Z`는 비교 가능한 이력이 3개 미만이거나 분산이 0이면 생략하므로 초기 사용자에게는 사실상 크기+볼륨 게이트만 작동한다.
- **부분 주 볼륨 2배 규칙**(`n<=2`)이 실무에서 너무 보수적인지.
- 다중 프로젝트 · 소재/예산/구성 라우터 확장(§5.5의 "나중" 행).


### 13.3 #812 검토에서 확인한 누락과 수정

공통 CSV의 `campaign_name`과 합성 fixture의 `campaign`이 달라 실제 업로드가 실패했고, 저장 스냅샷이 있어도 previous 데이터 없는 입력을 먼저 차단했다. `/weekly-review`의 efficiency 그룹 등록, 직접 업로더, 분석 게이트, 동일 기간/통화의 저장 집계 fallback으로 보완했다. 회귀는 실제 플랫폼형 헤더를 업로드하고 새로고침 후 다음 기간 파일만 넣는 브라우저 경로로 검증한다.

보고서 EN 누락, 선택 KPI와 CPA 고정 문구, 유지 목표 자동 합격, 결과 비중을 예산 믹스로 설명하는 오류도 수정했다. 저장되지 않은 폼 편집은 보고서의 저장 결정에 반영하지 않는다. 신규 사용자는 이전 결정함 이동 안내 대상이 아니며, 기존 안내는 키보드 포커스 진입·순환·복귀를 지원한다.

수익화 검증의 다음 단위는 도구 추가가 아니라 이 주간 루프다. 실데이터 임계값 튜닝·반복 사용률·지불 의향은 아직 실측하지 않았다. 구매/라이선스는 이 결과와 운영 조건을 확정한 다음 단계다.
