새 기능 하나 낼 때마다 이벤트 이름을 그때그때 짓다 보면, 6개월 뒤엔 `addToCart`, `add_cart`, `cart_add`가 한 서비스에 다 섞여 있어요. 사람은 대충 알아보지만 매체 최적화 알고리즘과 대시보드는 그렇지 못합니다. 이벤트 택소노미는 이걸 막는 **이름·파라미터·발화 시점의 표준 계약**이에요.

## 왜 이름 하나가 이렇게 중요한가

이벤트명은 그냥 라벨이 아니다. Google UAC·Meta AAP 같은 자동입찰 캠페인이 "성과가 좋았다/나빴다"를 판단하는 학습 신호가 바로 이 이벤트예요.

그래서 이름을 함부로 바꾸면 큰일이 납니다. 오늘 `purchase`로 보내던 걸 다음 주 `order_complete`로 바꾸면, 매체 입장에선 데이터가 0인 완전히 새로운 이벤트가 생긴 거다. **캠페인 학습이 통째로 리셋**되고, 다시 데이터가 쌓일 때까지 성과가 출렁여요. 이름은 코드 리팩터링하듯 가볍게 바꾸는 대상이 아니에요.

## 최소한 지켜야 할 것들

- **snake_case 통일**: `addToCart`(X) → `add_to_cart`(O). 대소문자·구분자 혼용을 처음부터 금지한다.
- **매체 예약어 회피**: `session_start`, `first_open`처럼 MMP·SDK가 이미 자동으로 쓰는 이름을 자체 이벤트로 다시 쓰면 충돌해요.
- **PII 절대 금지**: 이메일·전화번호·이름을 파라미터 값에 직접 넣지 않는다. 필요하면 해시 처리한 값만.
- **통화 코드 동반**: `revenue`를 보낼 땐 `currency`(ISO 4217, 예: KRW)를 항상 같이 보내세요. 매출 정규화는 서버에서 하고, 클라이언트는 원본 통화 그대로 보내는 게 안전합니다.

## 실무에서 진짜 자주 터지는 문제들

- **매출이 매체 대시보드에서 계속 0으로 보인다**: `currency` 누락이거나, 매체 파트너 설정에서 그 이벤트가 "Revenue Event"로 체크가 안 돼 있는 경우가 대부분이에요.
- **같은 결제가 여러 번 잡혀 ROAS가 부풀려진다**: 결제 콜백이 네트워크 재시도로 중복 발화되는 상황이다. `transaction_id`를 유니크 dedup 키로 강제하고, 서버 검증이 끝난 뒤에만 클라이언트가 이벤트를 쏘게 하세요.
- **자동입찰이 학습을 못 벗어난다**: 최적화 대상 이벤트(예: `purchase`)의 주간 발화량이 너무 적으면 알고리즘이 수렴하지 못해요. 이럴 땐 일시적으로 상위 퍼널 이벤트(`add_to_cart` 등)로 최적화 목표를 낮춰 학습량부터 채운다.

이 문제들은 대부분 소재나 입찰이 아니라 **측정 설계**에서 비롯돼요. 성과가 이상할 때 소재부터 갈아엎기 전에 이벤트가 제대로 들어오는지 먼저 확인하는 습관이 시간을 아껴줍니다.

## 정직하게

택소노미는 한 번 정하면 자주 못 바꾼다. 이벤트명을 바꾸면 과거 데이터와 단절되고 매체 학습도 다시 시작해야 하니까요. 그래서 처음 설계할 때 [인앱 이벤트 택소노미 설계서](/guide/event-taxonomy)처럼 퍼널 전체를 놓고 한 번에 정하는 편이, 나중에 하나씩 고쳐 쓰는 것보다 훨씬 싸게 먹혀요.
